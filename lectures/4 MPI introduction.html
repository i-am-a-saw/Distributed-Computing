Point-to-point communication in MPI

One process sends, one process receives. This handbook covers everything in the lecture notes, corrects the mistakes in them, and marks clearly where it adds material from outside the lecture.

How to read this

Russian terms from the lecture appear in italics, so you can match this page to your notes. Blocks marked Beyond the lecture are extra context checked against the MPI standard or official documentation. They are useful but not in your notes.

Corrections to the lecture notes

I checked every statement in the notes. These are the places where the notes are wrong or would not work as written. Each correction is repeated in the relevant section below.

  • Section on MPI_Send variants Notes: MPI_Isend is the blocking variant, MPI_Ssend is the non-blocking one.
    Correct: it is the other way round. MPI_Isend is non-blocking (the “I” means immediate). MPI_Ssend is a blocking synchronous send: it returns only after the matching receive has started.
  • Wildcard arguments Notes: pass MPI_ANY_SOURCE as the 3rd argument and MPI_ANY_TAG as the 4th.
    Correct: in MPI_Recv the source is the 4th argument and the tag is the 5th. The 3rd argument is the datatype.
  • Deadlock example, line 5 Notes: else if (my_rank == 0)
    Correct: else if (my_rank == 1). As printed, the second branch can never run, so process 1 would do nothing at all. The surrounding text clearly means process 1.
  • Running on two machines Notes: mpiexec -hosts 2 ip_1 ip_2
    Correct for Open MPI (the library the notes install): mpiexec --host ip_1,ip_2 -n 2 ./prog. The notes' command also leaves out the program name. I could not find documentation for the -hosts 2 ip_1 ip_2 form in current Open MPI or MPICH, so I can't confirm it ever worked. See section 2.
  • Minor The listing reference shows as “листинг ??” (a broken LaTeX reference), and “строки 14 и 15” refer to the MPI_Comm_size / MPI_Comm_rank lines. Line numbers were not printed in the PDF, so I refer to those calls by name instead.

1The distributed-memory model

MPI (Message Passing Interface) is an API for parallel and distributed computing. It assumes distributed memory (распределённая память): each process can read and write only its own memory. Processes are connected by a network. If process 2 needs a value that lives in process 0’s memory, process 0 has to send it as a message.

Point-to-point communication (точечные коммуникации) means one specific sender and one specific receiver, using MPI_Send and MPI_Recv. (Later lectures usually cover collective operations, where a whole group takes part.)

2Install, compile, run

Install Open MPI on Ubuntu

Shell
sudo apt install openmpi-bin openmpi-doc libopenmpi-dev
  • openmpi-bin: the tools mpicc, mpiexec, mpirun.
  • libopenmpi-dev: the header mpi.h and libraries you compile against.
  • openmpi-doc: man pages (e.g. man MPI_Send). I confirmed all three packages exist in current Ubuntu releases.

Compile

Shell
mpicc prog.c -o prog

mpicc is a wrapper around your normal C compiler (usually gcc). It adds the MPI include paths and libraries for you.

Run on one machine

Shell
mpiexec -n 4 ./prog

This starts 4 processes (4 copies of the same program). Each copy gets a different rank: 0, 1, 2, 3. In Open MPI, mpiexec and mpirun are the same command.

Beyond the lecture

If you ask for more processes than your machine has cores, Open MPI refuses to start. Add --oversubscribe (Open MPI 4.x, which Ubuntu 24.04 ships). In Open MPI 5.x the documented form is --map-by :OVERSUBSCRIBE. Check your version with mpirun --version.

Run on two machines

Corrected

The notes give mpiexec -hosts 2 ip_1 ip_2. That form is not in the current documentation and has no program name. Use one of these:

Open MPI (what the notes install)
mpiexec --host ip_1,ip_2 -n 2 ./prog
# more processes per machine: host:slots
mpiexec --host ip_1:4,ip_2:4 -n 8 ./prog
MPICH (Hydra launcher)
mpiexec -hosts ip_1,ip_2 -n 2 ./prog

For this to work, each machine needs:

  • password-less SSH login from the machine where you type the command,
  • the same MPI installed and on the PATH,
  • the compiled ./prog at the same path.

3Anatomy of an MPI program

Here is the lecture’s “greetings” program with comments. Every process runs this same code; the if on the rank decides who does what.

greetings.c
#include <mpi.h>
#include <string.h>
#include <stdio.h>
#define MAX_SIZE 100

int main() {
    int comm_sz;               // number of processes
    int my_rank;               // my number: 0 .. comm_sz-1
    char greeting[MAX_SIZE];

    MPI_Init(NULL, NULL);                       // start MPI
    MPI_Comm_size(MPI_COMM_WORLD, &comm_sz);    // how many of us?
    MPI_Comm_rank(MPI_COMM_WORLD, &my_rank);    // who am I?

    if (my_rank != 0) {
        // every worker: build a string and send it to process 0
        sprintf(greeting, "Greetings from process %d of %d",
                my_rank, comm_sz);
        MPI_Send(greeting, strlen(greeting) + 1,  // +1 for the '\0'
                 MPI_CHAR, 0, 0, MPI_COMM_WORLD);
    } else {
        // process 0: print own line, then receive from 1, 2, ... in order
        printf("Greetings from process %d of %d\n", my_rank, comm_sz);
        for (int i = 1; i < comm_sz; i++) {
            MPI_Recv(greeting, MAX_SIZE, MPI_CHAR,
                     i, 0, MPI_COMM_WORLD, MPI_STATUS_IGNORE);
            printf("%s\n", greeting);
        }
    }

    MPI_Finalize();                              // shut MPI down
    return 0;
}

With mpiexec -n 4 ./prog it prints:

Output
Greetings from process 0 of 4
Greetings from process 1 of 4
Greetings from process 2 of 4
Greetings from process 3 of 4

The order is always 1, 2, 3 because process 0 asks for rank 1 first, then rank 2, then rank 3, even if rank 3 was ready earlier. Section 6 shows how to take messages in whatever order they arrive.

I could not compile and run this code here (MPI could not be installed in my environment), so the output above is the expected result from reading the code, not a captured run. The code has no errors I can find.

MPI_Init and MPI_Finalize

All MPI calls must sit between MPI_Init and MPI_Finalize.

  • MPI_Init(&argc, &argv) sets MPI up: it takes pointers to the command-line arguments (passing NULL, NULL is allowed), prepares buffers for messages, and assigns a rank to each process.
  • MPI_Finalize() frees everything MPI allocated. No MPI calls after it.

4MPI_Send

Signature (as in the MPI standard)
int MPI_Send(const void *buf, int count, MPI_Datatype datatype,
             int dest, int tag, MPI_Comm comm);

The notes write the 3rd parameter without a name and call the 2nd one size; the standard names are shown above. It returns an error code (MPI_SUCCESS on success).

#ArgumentMeaning
1bufWhere the data is stored
2countHow many elements (not bytes)
3datatypeType of each element: MPI_CHAR, MPI_INT, MPI_DOUBLE, …
4destRank of the receiver
5tagA number you choose to label the message, so the receiver can tell what kind of data it is
6commThe communicator

Memory aid: arguments 1–3 describe the message (where, how many, what type). Arguments 4–6 describe the envelope (to whom, which label, in which group).

5MPI_Recv

Signature
int MPI_Recv(void *buf, int count, MPI_Datatype datatype,
             int source, int tag, MPI_Comm comm,
             MPI_Status *status);
#ArgumentMeaning
1bufWhere to write the received data
2countThe maximum number of elements that fit in buf
3datatypeType of each element
4sourceRank of the sender (or MPI_ANY_SOURCE)
5tagExpected tag (or MPI_ANY_TAG)
6commThe communicator
7statusOutput: who actually sent it and with what tag. Pass MPI_STATUS_IGNORE if you don’t need it.
Key difference from Send

When MPI_Recv returns, the message has arrived and is in your buffer. When MPI_Send returns, you don’t know whether the receiver got it yet (see section 7).

6Wildcards and MPI_Status

The problem

Several processes send to process 0. Process 5 is ready to send, but process 1 is still computing. If process 0 is waiting in MPI_Recv(..., source = 1, ...), it can’t leave that call until process 1’s message arrives. Meanwhile process 5’s message sits unused and the network idles.

The fix: wildcard arguments

Corrected

The notes say “3rd and 4th argument”. The correct positions are the 4th (source) and 5th (tag).

  • MPI_ANY_SOURCE as source: accept a message from any sender.
  • MPI_ANY_TAG as tag: accept a message with any tag.

You can use one of them or both. Then process 0 takes whichever message is ready first.

The new problem: who sent it, and how big was it?

With wildcards you no longer know the sender or the tag in advance, and you may not know the size either. So you pass a real MPI_Status variable instead of MPI_STATUS_IGNORE:

Receive from anyone, then inspect
MPI_Status status;
int buf[100], count;

MPI_Recv(buf, 100, MPI_INT, MPI_ANY_SOURCE, MPI_ANY_TAG,
         MPI_COMM_WORLD, &status);

int sender = status.MPI_SOURCE;            // who sent it
int tag    = status.MPI_TAG;               // which tag it had
MPI_Get_count(&status, MPI_INT, &count);  // how many ints actually arrived
You wantRead it from
Sender’s rankstatus.MPI_SOURCE
Message tagstatus.MPI_TAG
Number of elements receivedMPI_Get_count(&status, datatype, &count)
Beyond the lecture

MPI_Status also has a field MPI_ERROR. To learn a message’s size before receiving it (for example, to allocate a buffer), the standard provides MPI_Probe: it waits for a matching message and fills a status without receiving the data.

7What happens inside MPI_Send

First the data is packed into an envelope («конверт»): the data plus service information (sender, receiver, tag, communicator). Then one of two things happens:

  1. Buffered (кэширование): MPI copies the message into its internal memory and MPI_Send returns right away. Typical for small messages.
  2. Wait for the receiver: the transfer starts only when the receiver calls the matching MPI_Recv, and MPI_Send blocks until then. Typical for messages above a threshold.

So after MPI_Send returns, you only know that your buffer is safe to reuse. You don’t know whether the message was delivered.

Beyond the lecture

These two behaviours are usually called the eager protocol and the rendezvous protocol. The threshold between them depends on the MPI implementation and its settings.

Variants of Send

Corrected

The notes swap these two. The table shows the correct meaning.

Beyond the lecture

A useful debugging trick: replace MPI_Send with MPI_Ssend. If your program then hangs, it was relying on buffering and could deadlock with larger messages.

8When does a Send meet a Recv?

Process q calls

MPI_Send(send_buf_p, send_buf_sz, send_type, dest, send_tag, send_comm);

and process r calls

MPI_Recv(recv_buf_p, recv_buf_sz, recv_type, source, recv_tag, recv_comm, &status);

For the two calls to match

  • 1recv_comm == send_comm (same communicator)
  • 2recv_tag == send_tag, or the receiver used MPI_ANY_TAG
  • 3dest == r and source == q, or the receiver used MPI_ANY_SOURCE

For the data to arrive correctly, also

  • 4recv_type == send_type
  • 5recv_buf_sz ≥ send_buf_sz: the receive buffer is at least as big as the message
Beyond the lecture

If the message is larger than the receive buffer, MPI reports an overflow error (MPI_ERR_TRUNCATE). If it is smaller, that’s fine: only part of the buffer is filled, and MPI_Get_count tells you how much.

Message order (порядок сообщений)

SituationGuarantee
q sends two messages to rOrdered. The first one sent becomes available to r before the second. Messages don’t overtake each other.
Two different processes send to rNo guarantee. Which one is available first depends on timing and the network.

Precisely, the standard’s ordering rule applies when both messages could match the same receive (same communicator; the receive’s source and tag accept both). If r asks for a specific tag, it can still receive a later message with that tag first.

9Deadlock

Deadlock (взаимная блокировка): several processes each wait for something that another one holds, so none of them can continue.

The classic example: swapping arrays

Two processes want to exchange their arrays a (10 000 ints each). Line 5 is corrected:

Deadlocks for large messages
1  if (my_rank == 0) {
2      MPI_Send(a, 10000, MPI_INT, 1, 0, MPI_COMM_WORLD);
3      MPI_Recv(a, 10000, MPI_INT, 1, 0, MPI_COMM_WORLD, MPI_STATUS_IGNORE);
4  }
5  else if (my_rank == 1) {           // notes say == 0: a typo
6      MPI_Send(a, 10000, MPI_INT, 0, 0, MPI_COMM_WORLD);
7      MPI_Recv(a, 10000, MPI_INT, 0, 0, MPI_COMM_WORLD, MPI_STATUS_IGNORE);
8  }

The notes write &a. If a is an array, &a and a point to the same address, so it still works; plain a is the usual way to write it.

Why: the array is large, so MPI_Send waits for the receiver (section 7). Process 0 blocks on line 2, waiting for process 1 to call Recv. Process 1 blocks on line 6, waiting for process 0 to call Recv. Neither ever gets there.

Trap

With short messages (single variables instead of arrays), this code will probably work, because Send just buffers the message and returns. The code is still wrong: it relies on buffering that MPI doesn’t promise, and it will hang once the data grows.

10The fix: MPI_Sendrecv

MPI_Sendrecv performs a send and a receive as one call. MPI itself arranges the two transfers so they can’t block each other.

Signature
int MPI_Sendrecv(
    const void *sendbuf, int sendcount, MPI_Datatype sendtype,
    int dest,   int sendtag,
    void *recvbuf,       // OUT
    int recvcount, MPI_Datatype recvtype,
    int source, int recvtag,
    MPI_Comm comm,
    MPI_Status *status    // OUT
);

Read it as: the first 5 arguments are a Send, the next 5 are a Recv, then one shared communicator and a status.

Beyond the lecture

The MPI standard requires sendbuf and recvbuf to be different, non-overlapping memory. If you want to send and receive into the same array, use MPI_Sendrecv_replace below.

Swap fixed with MPI_Sendrecv (two arrays)
int partner = (my_rank == 0) ? 1 : 0;
MPI_Sendrecv(a, 10000, MPI_INT, partner, 0,     // send my a
             b, 10000, MPI_INT, partner, 0,     // receive into b
             MPI_COMM_WORLD, MPI_STATUS_IGNORE);

Same buffer for both: MPI_Sendrecv_replace

Signature
int MPI_Sendrecv_replace(
    void *buf,           // OUT: sent from, then overwritten
    int count, MPI_Datatype datatype,
    int dest,   int sendtag,
    int source, int recvtag,
    MPI_Comm comm,
    MPI_Status *status    // OUT
);
Swap fixed with one array
int partner = (my_rank == 0) ? 1 : 0;
MPI_Sendrecv_replace(a, 10000, MPI_INT,
                     partner, 0,   // send to partner, tag 0
                     partner, 0,   // receive from partner, tag 0
                     MPI_COMM_WORLD, MPI_STATUS_IGNORE);

Both processes run the same line, and no if is needed beyond choosing the partner.

Beyond the lecture

Another common fix is to change the order on one side: process 0 does Send then Recv, process 1 does Recv then Send. That also avoids the deadlock, but the two transfers then happen one after another instead of together.

Cheat sheet

Program frame

MPI_Init → MPI_Comm_size / MPI_Comm_rank → work → MPI_Finalize

Send

(buf, count, type, dest, tag, comm)
Returns: buffer reusable. Not proof of delivery.

Recv

(buf, count, type, source, tag, comm, status)
Returns: message received.

Wildcards

MPI_ANY_SOURCE (arg 4), MPI_ANY_TAG (arg 5). Then read status.MPI_SOURCE, status.MPI_TAG, MPI_Get_count.

Match needs

Same comm, same tag, right ranks. For correct data: same type, receive buffer ≥ message.

Ordering

Same sender → same receiver: in order. Different senders: no guarantee.

Send variants

Ssend: blocking, waits for receiver. Isend: non-blocking, finish with MPI_Wait.

Deadlock fix

MPI_Sendrecv (two buffers) or MPI_Sendrecv_replace (one buffer).

Commands

mpicc prog.c -o prog
mpiexec -n 4 ./prog
mpiexec --host h1,h2 -n 2 ./prog

Self-check

Answer in your head first, then open.

Process 3 wants to send 50 doubles stored in x to process 0 with tag 7. Write the call.
MPI_Send(x, 50, MPI_DOUBLE, 0, 7, MPI_COMM_WORLD);
MPI_Send returned. Has the receiver got the message?
Not necessarily. The message may only have been copied into MPI’s internal buffer. You only know that your send buffer can be reused. (MPI_Recv returning does mean the message arrived.)
Which one is non-blocking: MPI_Isend or MPI_Ssend?
MPI_Isend. MPI_Ssend blocks until the matching receive has started. The lecture notes have these swapped.
You receive with MPI_ANY_SOURCE. How do you find out who sent the message and how many elements came?
Pass &status instead of MPI_STATUS_IGNORE. Then status.MPI_SOURCE is the sender, and MPI_Get_count(&status, type, &n) gives the element count.
Process 1 sends message A then message B to process 0 (same tag, same communicator). Process 2 sends message C to process 0. What order is guaranteed?
Only that A is available before B. Where C falls relative to A and B is not guaranteed.
The array-swap code works in your tests with int x but hangs with int a[10000]. Why?
Small messages are buffered, so both Sends return and both processes reach their Recv. Large messages make Send wait for the receiver, and both processes wait on each other forever: deadlock. Fix it with MPI_Sendrecv or MPI_Sendrecv_replace.
The sender sends 20 ints; the receiver posts MPI_Recv with count 10. What happens?
The message doesn’t fit, so MPI reports a truncation error (MPI_ERR_TRUNCATE). The receive count must be at least the size of the message. (From the MPI standard; the notes only state the ≥ rule.)
Can you use MPI_Sendrecv with the same array as send and receive buffer?
No, the standard requires the two buffers to be separate. Use MPI_Sendrecv_replace for one shared buffer.
