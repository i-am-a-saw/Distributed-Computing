Collective communication in MPI (part 1)

Lecture 4 was about one sender and one receiver. Here every process in a communicator takes part in one operation. The lecture builds the idea around one example: computing an integral in parallel.

How to read this

Russian terms from the lecture appear in italics. Blocks marked Beyond the lecture add context checked against the MPI standard or official documentation; they are not in your notes.

Corrections to the lecture notes

I checked every statement and every listing. Lecture 5 is mostly correct; the issues below are one real mistake, one hidden assumption, and a few imprecise phrasings. Each is repeated where it matters.

  • Property 2 of collectives Error Notes: “the call on line 59 can be replaced by” an if/else whose two branches are identical.
    Correct: as printed, the example demonstrates nothing. The point is that non-root processes may pass any output pointer, for example NULL. The intended version is almost certainly the one shown in section 8. I can’t know exactly what the lecturer meant to write in the else branch; NULL is the standard illustration.
  • Listings 1 and 2 Hidden assumption Both programs only work when n is divisible by the number of processes. Otherwise the last few trapezoids are silently skipped and the answer is wrong. I verified this numerically; see section 2.
  • MPI_Reduce signature Naming The signature names the 6th parameter dest, but the text calls it root. The standard name is root. The standard also declares the input buffer as const void *.
  • Property 3 Incomplete Notes: point-to-point messages match by communicator and tag.
    More precisely: by communicator, tag and sender/receiver ranks, as Lecture 4 stated.
  • MPI_Allreduce Imprecise Notes: Allreduce “comes down to” calling Reduce and then Bcast.
    More precisely: the result is the same as Reduce followed by Bcast. The MPI standard does not say how it is implemented, and libraries often use faster algorithms. Figure 2 shows one possible way, not the only one.

1The task: integrate with the trapezoid rule

We want the definite integral of f from a to b. Split [a, b] into n equal pieces of width h, approximate each piece by a trapezoid, and add the areas.

∫ab f(x) dx ≈ h2(f(a) + f(b)) + h(f(x1) + f(x2) + … + f(xn−1))
SymbolMeaning
nnumber of pieces (trapezoids)
h = (b − a) / nwidth of one piece (шаг разбиения)
x0 = a, xi = a + i·h, xn = bthe split points (узлы разбиения)

The ends f(a), f(b) get weight h/2 because each belongs to only one trapezoid. Every inner point belongs to two neighbouring trapezoids, so it gets weight h. I checked the formula: it is correct.

How the work is split

Each of the p processes takes local_n = n / p neighbouring trapezoids and computes their sum. Then the partial sums are added together.

2Version 1: only Send and Recv (Listing 1)

This is the lecture’s first attempt, using only the tools from Lecture 4. Read it in three parts: input, local work, collecting the result.

Listing 1, with comments
#include <mpi.h>
#include <string.h>
#include <stdio.h>

int n;  double a;  double b;     // global: the task, known to all after Input()
int comm_sz;  int my_rank;

double f(double x) { return x * x; }

void Input() {
    if (my_rank == 0) {
        printf("Enter a, b, n\n");
        scanf("%lf %lf %d", &a, &b, &n);
        for (int i = 1; i < comm_sz; i++) {     // 3 sends to EACH other process
            MPI_Send(&a, 1, MPI_DOUBLE, i, 0, MPI_COMM_WORLD);
            MPI_Send(&b, 1, MPI_DOUBLE, i, 0, MPI_COMM_WORLD);
            MPI_Send(&n, 1, MPI_INT,    i, 0, MPI_COMM_WORLD);
        }
    } else {
        MPI_Recv(&a, 1, MPI_DOUBLE, 0, 0, MPI_COMM_WORLD, MPI_STATUS_IGNORE);
        MPI_Recv(&b, 1, MPI_DOUBLE, 0, 0, MPI_COMM_WORLD, MPI_STATUS_IGNORE);
        MPI_Recv(&n, 1, MPI_INT,    0, 0, MPI_COMM_WORLD, MPI_STATUS_IGNORE);
    }
}

// serial trapezoid rule on [a, b] with n pieces of width h
double Trap(double a, double b, int n, double h) {
    double res = 0.5 * (f(a) + f(b));             // the two ends, weight 1/2
    for (int i = 1; i <= n - 1; i++) {
        double x = a + i * h;
        res += f(x);                                // inner points, weight 1
    }
    return res * h;
}

int main() {
    MPI_Init(NULL, NULL);
    MPI_Comm_size(MPI_COMM_WORLD, &comm_sz);
    MPI_Comm_rank(MPI_COMM_WORLD, &my_rank);

    Input();

    double h = (b - a) / n;                       // same h on every process
    int    local_n = n / comm_sz;                 // my number of trapezoids
    double local_a = a + my_rank * local_n * h;   // where my piece starts
    double local_b = local_a + local_n * h;       // where it ends
    double local_int = Trap(local_a, local_b, local_n, h);

    double global_int;
    if (my_rank != 0) {
        MPI_Send(&local_int, 1, MPI_DOUBLE, 0, 0, MPI_COMM_WORLD);
    } else {
        global_int = local_int;                     // process 0 adds everything, one by one
        for (int i = 1; i < comm_sz; i++) {
            MPI_Recv(&local_int, 1, MPI_DOUBLE, i, 0, MPI_COMM_WORLD, MPI_STATUS_IGNORE);
            global_int += local_int;
        }
    }
    if (my_rank == 0) printf("Int = %lf\n", global_int);

    MPI_Finalize();
    return 0;
}

Reusing local_int as the receive buffer on process 0 is safe: its own value was already copied into global_int.

Beyond the lecture

Why only process 0 calls scanf: in Open MPI, keyboard input (stdin) is forwarded to rank 0 only by default. The other processes get an empty input. That is why process 0 reads the numbers and then has to send them to everyone else.

The hidden assumption: n must divide evenly

Trap

local_n = n / comm_sz is integer division, so the remainder is thrown away. Those last trapezoids are never computed, and the program prints a wrong answer with no warning.

3The bottleneck, and the tree that fixes it

In Version 1, process 0 does all the adding. With p processes it receives and adds p − 1 values one after another, while all other processes sit idle. That takes time proportional to p: O(p).

A better plan is a tree (древовидная структура): pair processes up and add in parallel. Each round halves the number of values still in play, so only about log₂ p rounds are needed: O(log p).

You don’t write this tree yourself. MPI provides it as one call: MPI_Reduce.

Beyond the lecture

The MPI standard says what MPI_Reduce computes, not how. A tree like Figure 1 is a typical way to do it, but each library chooses its own algorithm.

4MPI_Reduce

A collective communication (коллективная коммуникация): every process contributes a value, MPI combines them with an operation (sum, max, …), and the result lands on one process, the root.

Signature (MPI standard)
int MPI_Reduce(const void *sendbuf,     /* in  */
               void       *recvbuf,     /* out, used only on root */
               int         count,       /* in  */
               MPI_Datatype datatype,   /* in  */
               MPI_Op      op,          /* in  */
               int         root,        /* in  */
               MPI_Comm    comm);       /* in  */
#Lecture nameStandard nameMeaning
1input_buf_psendbufMy contribution
2output_buf_precvbufWhere the result goes. Only matters on the root.
3countcountNumber of elements
4datatypedatatypeElement type
5operationopHow to combine: MPI_SUM, MPI_MAX, …
6dest (text: root)rootRank that receives the result
7CommunicatorcommWhich processes take part

In the integral program, the whole collection loop from Version 1 becomes:

MPI_Reduce(&local_int, &global_int, 1, MPI_DOUBLE, MPI_SUM, 0, MPI_COMM_WORLD);

Available operations

The lecture mentions sum, product, minimum, maximum, logical and bitwise operations, and user-defined ones. The predefined names are:

OperationMeaning
MPI_SUM, MPI_PRODsum, product
MPI_MAX, MPI_MINmaximum, minimum
MPI_LAND, MPI_LOR, MPI_LXORlogical AND, OR, XOR
MPI_BAND, MPI_BOR, MPI_BXORbitwise AND, OR, XOR
MPI_MAXLOC, MPI_MINLOCmax / min together with the rank (or index) where it was found

Your own operation is created with MPI_Op_create.

Beyond the lecture
  • Arrays are combined element by element. With count = 3, element 0 of all processes is combined into result element 0, element 1 into element 1, and so on.
  • Floating-point sums may differ slightly between runs. MPI assumes the operation is associative and may add in any order. For doubles, a different order can change the last digits.

5MPI_Bcast

Broadcast: one process (the root) sends the same data to all other processes in the communicator. It is the opposite direction of Reduce.

Signature (MPI standard)
int MPI_Bcast(void        *buffer,     /* in on root, out on all others */
              int          count,
              MPI_Datatype datatype,
              int          root,       /* lecture: source_proc */
              MPI_Comm     comm);
Key idea

There is one buffer, and its role depends on who you are. On the root it holds the data to send. On every other process MPI overwrites it with the received copy. All processes call exactly the same line.

Input() becomes three lines
if (my_rank == 0) scanf("%lf %lf %d", &a, &b, &n);   // only root reads
MPI_Bcast(&a, 1, MPI_DOUBLE, 0, MPI_COMM_WORLD);         // everyone calls
MPI_Bcast(&b, 1, MPI_DOUBLE, 0, MPI_COMM_WORLD);
MPI_Bcast(&n, 1, MPI_INT,    0, MPI_COMM_WORLD);

6MPI_Allreduce

Same as MPI_Reduce, but every process gets the result, not only the root. Because nobody is special, there is no root argument.

Signature (MPI standard)
int MPI_Allreduce(const void *sendbuf,
                  void       *recvbuf,     /* result on EVERY process */
                  int         count,
                  MPI_Datatype datatype,
                  MPI_Op      op,
                  MPI_Comm    comm);        /* note: no root */
Clarified

The notes say Allreduce “comes down to” Reduce followed by Bcast. That is true for the result. The standard does not fix the algorithm, and libraries may use faster schemes that finish in fewer rounds than the two trees above.

FunctionData flowWho has the resultRoot argument?

MPI_Bcastone → manyeveryone (a copy)yes
MPI_Allreducemany → alleveryoneno

7Version 2: with collectives (Listing 2)

The same program, rewritten. Changed lines are highlighted in green. I checked the listing: it is correct (with the same n-divisible-by-p assumption as Version 1).

Listing 2, with comments
#include <mpi.h>
#include <string.h>
#include <stdio.h>

int n;  double a;  double b;
int comm_sz;  int my_rank;

double f(double x) { return x * x; }

void Input() {
    if (my_rank == 0) {
        printf("Enter a, b, n\n");
        scanf("%lf %lf %d", &a, &b, &n);
    }
    MPI_Bcast(&a, 1, MPI_DOUBLE, 0, MPI_COMM_WORLD);   // all processes call these
    MPI_Bcast(&b, 1, MPI_DOUBLE, 0, MPI_COMM_WORLD);
    MPI_Bcast(&n, 1, MPI_INT,    0, MPI_COMM_WORLD);
}

double Trap(double a, double b, int n, double h) {
    double res = (f(a) + f(b)) / 2.0;             // same as 0.5 * (...) in Listing 1
    for (int i = 1; i <= n - 1; i++) {
        double x = a + i * h;
        res += f(x);
    }
    return h * res;
}

int main() {
    MPI_Init(NULL, NULL);
    MPI_Comm_size(MPI_COMM_WORLD, &comm_sz);
    MPI_Comm_rank(MPI_COMM_WORLD, &my_rank);

    Input();

    int    local_n = n / comm_sz;
    double h = (b - a) / n;
    double local_a = a + my_rank * local_n * h;
    double local_b = local_a + local_n * h;
    double local_int = Trap(local_a, local_b, local_n, h);
    double global_int = 0.0;

    MPI_Reduce(&local_int, &global_int, 1, MPI_DOUBLE,
               MPI_SUM, 0, MPI_COMM_WORLD);           // replaces the whole Send/Recv loop

    if (my_rank == 0) printf("Int = %lf\n", global_int);

    MPI_Finalize();
    return 0;
}

8Three rules of collective calls

Rule 1. Every process in the communicator must make the call

If even one process skips it, the result is undefined. In practice the program usually hangs, because the others wait for a contribution that never comes.

Beyond the lecture

All processes must also pass the same count, datatype, op, root and communicator. Only the buffers may differ.

Rule 2. The output buffer matters only on the root

For MPI_Reduce, only the root’s recvbuf receives anything. On other processes you can pass anything, even NULL.

Corrected

In the notes, both branches of the example are identical, so they show nothing. This is what the example is meant to show:

if (my_rank == 0)
    MPI_Reduce(&local_int, &global_int, 1, MPI_DOUBLE, MPI_SUM, 0, MPI_COMM_WORLD);
else
    MPI_Reduce(&local_int, NULL,        1, MPI_DOUBLE, MPI_SUM, 0, MPI_COMM_WORLD);
Beyond the lecture

Don’t pass the same variable as both input and output, like MPI_Reduce(&x, &x, ...). The standard forbids this aliasing. If you want the result to overwrite the input, pass MPI_IN_PLACE as sendbuf on the root.

Rule 3. Collectives match by communicator and call order, not by tags

Point-to-point messages are matched by communicator, tag, and sender/receiver ranks. Collective calls have no tags. MPI matches them only by communicator and the order in which each process calls them: every process’s 1st collective call goes together, then every 2nd, and so on. Variable names play no role.

Listing 3, run with 3 processes
int a = 1;  int c = 2;
int b = 0;  int d = 0;

if (my_rank == 0 || my_rank == 2) {
    MPI_Reduce(&a, &b, 1, MPI_INT, MPI_SUM, 0, MPI_COMM_WORLD);   // 1st call
    MPI_Reduce(&c, &d, 1, MPI_INT, MPI_SUM, 0, MPI_COMM_WORLD);   // 2nd call
} else {
    MPI_Reduce(&c, &d, 1, MPI_INT, MPI_SUM, 0, MPI_COMM_WORLD);   // 1st call
    MPI_Reduce(&a, &b, 1, MPI_INT, MPI_SUM, 0, MPI_COMM_WORLD);   // 2nd call
}
if (my_rank == 0) printf("b = %d, d = %d\n", b, d);

A reader might expect b = 1+1+1 = 3 and d = 2+2+2 = 6. But MPI pairs up the calls by order:

CallProcess 0 sendsProcess 1 sendsProcess 2 sendsSumStored in (root’s recvbuf)
1sta = 1c = 2a = 14b
2ndc = 2a = 1c = 25d

Output: b = 4, d = 5, as the lecture says. I verified this by walking through the calls. The result is stored in b and d because those are the output buffers process 0 (the root) passed in its 1st and 2nd calls.

Cheat sheet

Trapezoid rule

h = (b − a)/n. Sum = h·[(f(a)+f(b))/2 + f(x₁)+…+f(xₙ₋₁)]

Work split

local_n = n/p, local_a = a + rank·local_n·h. Needs n divisible by p.

MPI_Reduce

(sendbuf, recvbuf, count, type, op, root, comm)
many → one. recvbuf used only on root.

MPI_Bcast

(buffer, count, type, root, comm)
one → many. Same buffer: in on root, out elsewhere.

MPI_Allreduce

(sendbuf, recvbuf, count, type, op, comm)
many → all. No root.

Operations

MPI_SUM PROD MAX MIN, logical LAND LOR LXOR, bitwise BAND BOR BXOR, MAXLOC MINLOC, custom via MPI_Op_create.

Cost

Process 0 sums alone: O(p). Tree: O(log p).

Rules

1) all processes call. 2) output only on root. 3) matched by comm + call order, no tags.

Self-check

Answer in your head first, then open.

What is the main weakness of Version 1 (Listing 1)?
Process 0 receives and adds all partial sums by itself, one after another: O(p) time while the others sit idle. A tree reduction does it in O(log p) rounds.
Write the call that puts the maximum of every process’s double t into tmax on process 0.
MPI_Reduce(&t, &tmax, 1, MPI_DOUBLE, MPI_MAX, 0, MPI_COMM_WORLD);
Every process needs the global sum, not just process 0. Which function, and why does it have no root?
MPI_Allreduce. The result goes to everyone, so no single destination needs to be named.
In MPI_Bcast, is the buffer input or output?
Both. On the root it is the input (the data to send). On every other process it is the output (overwritten with the received copy).
You run Version 2 with n = 10 on 4 processes, for x² on [0, 3]. Is the answer right?
No. local_n = 10/4 = 2, so only 8 of the 10 trapezoids are computed, covering [0, 2.4]. The program prints about 4.644 instead of about 9.
Process 2 forgets to call MPI_Reduce. What happens?
The behaviour is undefined; in practice the program usually hangs, since the collective can’t complete without process 2’s contribution.
Why does Listing 3 print b = 4, d = 5 instead of 3 and 6?
Collectives have no tags. MPI matches each process’s 1st call with the others’ 1st call, and so on. In the 1st call, processes 0 and 2 send a = 1 while process 1 sends c = 2: total 4, stored in the root’s b. The 2nd call gives 2 + 1 + 2 = 5, stored in d.
Can you write MPI_Reduce(&x, &x, 1, MPI_INT, MPI_SUM, 0, comm)?
No, the input and output buffers must not be the same memory. On the root, pass MPI_IN_PLACE as the first argument instead.
