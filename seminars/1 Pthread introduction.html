01

POSIX Threads и подготовка среды

Что такое pthreads и как запустить программу.

Pthreads (POSIX Threads) — стандартный POSIX API для работы с потоками. Его реализации есть во многих UNIX-подобных системах, например GNU/Linux, Solaris, FreeBSD, OpenBSD, NetBSD и macOS. Конспект рекомендует пользователям Windows установить WSL (Windows Subsystem for Linux), а затем запускать среду Ubuntu.

🧵

Процесс и поток

Процесс — работающая программа со своим адресным пространством. Потоки внутри процесса выполняются независимо по расписанию, но обычно разделяют адресное пространство: глобальные переменные и динамически выделенная память доступны всем потокам этого процесса.

У каждого потока при этом есть собственный стек и собственное состояние выполнения.

⚙️

Почему именно pthreads?

Конспект сравнивает логику управления с C++ std::thread. В Unix-системах реализация потоков C++ часто использует системные примитивы pthreads. Pthreads даёт низкоуровневый контроль: атрибуты потока, идентификатор, ожидание завершения и отмену. Это полезно в системном и высокопроизводительном коде, включая real-time и HFT.

Низкоуровневый API сам по себе не гарантирует большую скорость: она зависит от задачи, синхронизации и накладных расходов.

Установка и компиляция

02

Первый многопоточный Hello, world!

Что делает каждая часть программы из листинга 1.

Главная идея: поток создаётся вызовом pthread_create, а переданная ему функция выполняется конкурентно с кодом main. «Конкурентно» не означает, что строки обязательно выполнятся в порядке создания. Планировщик ОС решает, какой поток когда получит процессор.

hello.c · полный компактный пример
#include <stdio.h>
#include <stdlib.h>
#include <pthread.h>

static long thread_count;

static void *routine(void *arg) {
    const long *rank_ptr = arg;
    long rank = *rank_ptr;
    printf("Hello from thread %ld of %ld\n", rank, thread_count);
    return NULL;
}

int main(int argc, char **argv) {
    if (argc != 2) {
        fprintf(stderr, "Usage: %s THREADS\n", argv[0]);
        return EXIT_FAILURE;
    }

    char *end = NULL;
    long n = strtol(argv[1], &end, 10);
    if (*argv[1] == '\0' || *end != '\0' || n < 1 || n > 10000) {
        fprintf(stderr, "THREADS must be an integer in [1, 10000]\n");
        return EXIT_FAILURE;
    }
    thread_count = n;
    pthread_t *threads = malloc((size_t)n * sizeof *threads);
    long *ranks = malloc((size_t)n * sizeof *ranks);
    if (threads == NULL || ranks == NULL) {
        perror("malloc");
        free(threads);
        free(ranks);
        return EXIT_FAILURE;
    }

    long created = 0;
    for (long i = 0; i < n; ++i) {
        ranks[i] = i;
        int err = pthread_create(&threads[i], NULL, routine, &ranks[i]);
        if (err != 0) {
            fprintf(stderr, "pthread_create: error %d\n", err);
            break;
        }
        ++created;
    }

    puts("Hello from main thread");
    for (long i = 0; i < created; ++i) {
        int err = pthread_join(threads[i], NULL);
        if (err != 0) fprintf(stderr, "pthread_join: error %d\n", err);
    }
    free(ranks);
    free(threads);
    return created == n ? EXIT_SUCCESS : EXIT_FAILURE;
}
Почему передаём указатель на отдельный элемент массива?

У каждого потока есть собственный элемент ranks[i]. Этот массив остаётся в памяти до завершения всех созданных потоков, поэтому аргументы не конфликтуют и не исчезают раньше времени.

Визуально: кто исполняется?

main()
создаёт потоки
→
routine(0)
routine(1)
routine(2)
Поток main
созданиепечатьjoin(0…N−1)
Рабочие потоки

Это схема отношений, а не точный порядок исполнения во времени: рабочие потоки могут напечатать строки до или после сообщения main.

Почему вывод может меняться?

После успешного pthread_create нет гарантии, что сначала продолжит выполняться вызывающий поток или немедленно начнёт рабочий. Поэтому строки в консоли могут идти в разном порядке. Порядок индексов в массиве threads не задаёт порядок печати.

Если программа создала четыре потока и сразу печатает сообщение из main, что гарантировано?

03

Создание потока: pthread_create

Четыре аргумента, идентификаторы и атрибуты.

Прототип из POSIX API
int pthread_create(
    pthread_t *thread,
    const pthread_attr_t *attr,
    void *(*start_routine)(void *),
    void *arg
);

1. pthread_t *thread

Адрес переменной, в которую функция запишет идентификатор нового потока. Обычно храним несколько идентификаторов в массиве:

pthread_t *threads;

Дескриптор нужен, например, чтобы потом вызвать pthread_join(threads[i], NULL).

2. attr

Атрибуты создаваемого потока: стек, параметры планирования и другие свойства. NULL означает использование атрибутов по умолчанию. Для явной настройки используется pthread_attr_t и функции pthread_attr_*.

3. start_routine

Указатель на функцию с точной сигнатурой void *function(void *). В ней выполняется работа потока. Возврат из функции эквивалентен завершению потока с возвращаемым указателем.

4. arg

Один указатель типа void *, передаваемый стартовой функции. Через него передают индекс, указатель на структуру, задачу или другие параметры.

Получить или сравнить идентификатор

pthread_self()

Возвращает идентификатор текущего потока:

pthread_t me = pthread_self();

pthread_equal(t1, t2)

Проверяет, обозначают ли два идентификатора один и тот же поток. Для POSIX-кода используйте именно эту функцию, а не предполагайте, что pthread_t — число, которое можно корректно сравнить обычным ==.

Передаём индивидуальные данные: безопасный шаблон

Нельзя передавать всем потокам адрес одной переменной цикла, а потом менять её: рабочие потоки могут прочитать уже изменённое значение. Выделите каждому потоку отдельную структуру, живущую до окончания работы потока.

Раздельные аргументы на весь срок выполнения
#include <stdio.h>
#include <stdlib.h>
#include <pthread.h>

struct Task { long rank; const char *title; };

static void *routine(void *arg) {
    const struct Task *task = arg;
    printf("rank=%ld title=%s\n", task->rank, task->title);
    return NULL;
}

int main(void) {
    enum { N = 3 };
    pthread_t threads[N];
    struct Task tasks[N];

    for (long i = 0; i < N; ++i) {
        tasks[i].rank = i;
        tasks[i].title = "worker";
        int err = pthread_create(&threads[i], NULL, routine, &tasks[i]);
        if (err != 0) {
            fprintf(stderr, "pthread_create: %d\n", err);
            return EXIT_FAILURE;
        }
    }
    for (int i = 0; i < N; ++i) pthread_join(threads[i], NULL);
    return EXIT_SUCCESS;
}

В примере массив tasks принадлежит main и не исчезает до join. Для динамической памяти правило то же: всегда заранее решите, кто владеет объектом и кто освобождает его.

Что опасно в таком цикле?

04

Завершение: join, detach и exit

Как дождаться результата и освободить ресурсы.

pthread_join — дождаться и забрать результат

Сигнатура
int pthread_join(pthread_t thread, void **retval);
  • Ожидает завершения одного конкретного потока, заданного в первом аргументе. Чтобы дождаться всех рабочих потоков, вызови join для каждого дескриптора в цикле.
  • Если retval != NULL, получает указатель, который поток вернул из стартовой функции или передал в pthread_exit.
  • У joinable-потока вызов join позволяет системе окончательно освободить ресурсы потока.
  • Функция возвращает 0 при успехе или код ошибки. Этот код обычно не нужно читать через errno.

pthread_detach — отказаться от join

Сигнатура
int pthread_detach(pthread_t thread);

Detached-поток не требует последующего pthread_join: когда он завершится, его системные ресурсы будут автоматически освобождены. Но получить его возвращаемое значение через join нельзя, а превратить отсоединённый поток обратно в joinable простым вызовом нельзя.

Поток освобождает ресурсы по завершении автоматически. Программа не получает результат через join и всё равно должна обеспечить, чтобы процесс жил достаточно долго.

Что за «зомби»-поток?

В конспекте сравниваются программы с join и detach при попытке создать очень много потоков (например, 100000). Идея правильная: завершившийся joinable-поток, которого никто не присоединил, может удерживать ресурсы. В Linux у системы есть лимиты на число потоков и память, поэтому создание огромного числа потоков может завершиться ошибкой.

Уточнение к листингу с detach

Detach не означает «можно создать неограниченное число потоков». Он освобождает ресурсы после завершения, а не предотвращает исчерпание ресурсов у большого числа одновременно работающих потоков. Кроме того, если main вернётся из main или процесс вызовет exit, все потоки процесса завершатся — даже detached. Вызов pthread_detach нужно делать только после успешного pthread_create.

pthread_exit — завершить текущий поток

Правильный прототип
void pthread_exit(void *retval);

Завершает поток, который вызвал функцию, и предоставляет retval потоку, который позднее выполнит pthread_join. В обычной стартовой функции return some_pointer; приводит к тому же результату. Не возвращай указатель на локальную переменную стека: к моменту получения результата её срок жизни закончится.

05

Сигналы, отмена и состояние отмены

Четыре функции, которые важно не путать.

pthread_kill: отправка сигнала

Сигнатура
int pthread_kill(pthread_t thread, int sig);

Функция посылает указанный сигнал определённому потоку (например, сигнал из <signal.h>). Название вводит в заблуждение: это не универсальная функция безопасного завершения потока. Действие сигнала определяется обработчиком и правилами сигналов POSIX. В частности, стандартное действие SIGQUIT — завершить процесс, а не аккуратно «убить только указанный поток». Для управления жизненным циклом чаще используют кооперативный флаг остановки или API отмены.

pthread_cancel: запрос на отмену

Сигнатура
int pthread_cancel(pthread_t thread);

Отправляет запрос на отмену. Это не обещание мгновенного убийства: поток может обработать запрос, выполнить очистку и завершиться в соответствии со своим состоянием отмены.

Состояние отмены

int pthread_setcancelstate(
    int state,
    int *oldstate
);

PTHREAD_CANCEL_ENABLE — запросы на отмену разрешены.

PTHREAD_CANCEL_DISABLE — запрос отмены не завершает поток, пока отмена отключена; запрос может оставаться ожидающим.

oldstate при необходимости получает предыдущее состояние.

Тип отмены

int pthread_setcanceltype(
    int type,
    int *oldtype
);

PTHREAD_CANCEL_DEFERRED — отложенная отмена, режим по умолчанию.

PTHREAD_CANCEL_ASYNCHRONOUS — отмена может произойти практически в любой момент.

Второй аргумент может сохранить предыдущий тип.

Передача структуры и возврат результата

Разбор идеи листинга 3.

В конспекте используется структура с двумя полями: rank (номер потока) и title (строка). Главный поток создаёт для каждого рабочего потока структуру, заполняет её и передаёт указатель как четвёртый аргумент pthread_create. Рабочий поток приводит void * обратно к struct S *, читает поля и выделяет отдельную структуру для результата.

main выделяет Task
rank, title
→

→

преобразовать тип

Полный пример: передать структуру и вернуть отдельный результат
#include <stdio.h>
#include <stdlib.h>
#include <pthread.h>

struct Task { long rank; const char *title; };
struct Result { long rank; const char *title; long answer; };

static void *routine(void *arg) {
    const struct Task *task = arg;
    struct Result *result = malloc(sizeof *result);
    if (result == NULL) return NULL;

    result->rank = task->rank;
    result->title = "return";
    result->answer = task->rank * 10;
    printf("thread %ld: %s\n", task->rank, task->title);
    return result;
}

int main(void) {
    enum { N = 3 };
    pthread_t threads[N];
    struct Task tasks[N];

    int created = 0;
    for (long i = 0; i < N; ++i) {
        tasks[i].rank = i;
        tasks[i].title = "Title";
        int err = pthread_create(&threads[i], NULL, routine, &tasks[i]);
        if (err != 0) {
            fprintf(stderr, "pthread_create: %d\n", err);
            break;
        }
        ++created;
    }
    for (int i = 0; i < created; ++i) {
        void *raw_result = NULL;
        int err = pthread_join(threads[i], &raw_result);
        if (err != 0) {
            fprintf(stderr, "pthread_join: %d\n", err);
            continue;
        }
        struct Result *result = raw_result;
        if (result == NULL) {
            fprintf(stderr, "thread %d returned no result (allocation may have failed)\n", i);
            continue;
        }
        printf("Return: rank=%ld title=%s answer=%ld\n",
               result->rank, result->title, result->answer);
        free(result);
    }
    return created == N ? EXIT_SUCCESS : EXIT_FAILURE;
}

Четыре правила владения памятью

  1. Аргументы: объект, на который указывает arg, должен жить столько, сколько поток его читает.
  2. Результат: возвращаемый указатель должен указывать на объект, который ещё существует после окончания функции. Не возвращайте адрес локального автоматического объекта.
  3. Владелец освобождения: если поток выделил результат через malloc, получивший результат main обычно отвечает за free.
  4. Строки: строковые литералы можно безопасно хранить через const char *. Не пытайтесь их изменять или освобождать через free.
Что следует улучшить в исходном листинге

В исходном примере память под входную структуру выделяется в main, но её адрес не сохраняется для дальнейшего free; это ведёт к утечке. Кроме того, нужен контроль ошибок malloc, pthread_create и pthread_join. Пример выше показывает раздельное владение аргументами и результатами; при ошибке создания части потоков производственный код также должен присоединить уже успешно созданные потоки.

07

Когерентность кэшей

Почему у разных ядер может быть локальная копия одних и тех же данных.

В примере из конспекта есть общая переменная x = 7 и два процессора. Процессор 1 вычисляет a = 2x, затем записывает x = 12. Процессор 2 сначала выполняет команды, которые не связаны с x, а затем вычисляет b = 10x. Какое значение получится у b — 70 или 120 — зависит от того, видит ли процессор 2 актуальное значение.

ВремяПроцессор 1Процессор 2

1x = 12Выполняет команды без x
2—b = 10x → 70 или 120
Гипотетический случай

Нет когерентности

Если у процессора 2 осталась устаревшая копия x = 7 и он не узнаёт об изменении, вычислит b = 70.

Когерентность поддерживается

Актуальная копия

Протокол когерентности обеспечивает согласованное состояние кэшированных копий: процессор 2 обнаружит, что старая копия недействительна, и получит актуальное значение. Тогда b = 120.

Когерентность кэша — аппаратные механизмы, поддерживающие согласованность копий данных в кэшах разных ядер/процессоров. В конспекте названы два подхода: отслеживание (snooping), когда узлы наблюдают за транзакциями на общей шине/интерконнекте, и справочник (directory), который отслеживает, где находятся копии строк.

Важно: пример с x — модель проблемы, а не нормальное поведение современной согласованной памяти

На обычной когерентной CPU-системе нельзя просто получить устаревшее значение из-за «необновлённого кэша» как законное поведение синхронизированной программы. Но если в C два потока читают/пишут одну обычную переменную без синхронизации, это уже data race и поведение программы не определено моделью памяти C. Аппаратная когерентность не заменяет mutex/атомики и не исправляет гонки данных.

False sharing — ложное совместное использование

Разные переменные, одна кэш-линия, лишний обмен.

False sharing возникает, когда разные ядра изменяют разные переменные, но эти переменные находятся в одной кэш-линии. Когерентность работает на уровне целой линии, а не отдельного поля или элемента массива. Поэтому кэш-линия может переходить между ядрами, хотя сами значения логически независимы.

Кэш-линия64 байта — типичный пример
8 элементов по 8 байт или 16 элементов по 4 байта

y[1]
y[2]
y[3]
y[4]
y[5]
y[6]
y[7]

Ядра записывают в разные элементы, но элементы находятся в одной линии. Нажми кнопки, чтобы увидеть передачу владения.

Это не data race

Если каждое ядро действительно пишет в свои индексы и никакой элемент не читается/пишется без синхронизации конфликтующими потоками, состояния гонки над элементами нет. Однако аппаратная линия всё равно может инвалидироваться из-за соседних записей.

Почему это «ложное» sharing?

Потоки не используют один и тот же элемент, то есть на уровне логики данных совместного доступа нет. Но железо поддерживает когерентность на более крупной единице — кэш-линии, поэтому платим за обмен данными без пользы для алгоритма.

Как обычно уменьшить false sharing

  1. Разнести часто изменяемые данные: добавить padding или выровнять независимые области по границе кэш-линии, если это уместно для целевой платформы.
  2. Считать локально: каждый поток накапливает результат в собственной локальной переменной/частной структуре; в конце main объединяет частичные результаты.
  3. Разбивать массив блоками: раздавать потокам непрерывные блоки, границы которых не делят кэш-линию между потоками.
  4. Сначала измерить: false sharing — проблема производительности, которая зависит от размеров данных и архитектуры. Подтверждать её лучше профилировщиком.
Нюанс о «добавить мусор»

Конспект советует добавить в выходной массив y «мусор», чтобы он перестал помещаться в одну линию. Сам по себе больший размер выделенной памяти проблему не гарантированно решает: важно, чтобы данные, которые независимо изменяются разными потоками, физически располагались в разных кэш-линиях или чтобы потоки писали в разные частные буферы. Полезный смысл рекомендации — разнести рабочие области, а не просто выделить лишние байты.

Умножение матрицы на вектор: код и результаты

Почему форма матрицы влияет на масштабирование.

Пусть матрица A размера n_rows × n_cols, вектор vec длины n_cols. Нужно вычислить вектор-результат res длины n_rows:

res[i] = ∑j=0n_cols−1 A[i·n_cols+j] · vec[j]

В C матрица хранится в одном плоском массиве в построчном порядке.

Визуализация одной строки результата

Строка A[i, *]
n_cols чисел
×
Вектор vec
n_cols чисел
→
Сумма произведений
один res[i]

Каждый индекс i результата вычисляется отдельной суммой. Это естественная единица работы для параллелизма по строкам.

Параллельное разбиение по строкам

В листинге 4 каждый поток получает набор строк. В исходном коде используются вычисления my_rows = n_rows / thread_count, my_first_i = my_rows * my_rank и my_last_i = (my_rank + 1) * my_rows - 1. Это корректно только когда n_rows делится на количество потоков без остатка. Иначе последняя часть строк будет потеряна.

Поиграй с размером

Калькулятор сравнивает формулу из конспекта с надёжным разбиением, которое распределяет все строки, даже если их число не делится на количество потоков.

Цикл вычисления из конспекта

Ядро вычисления
for (int i = my_first_i; i <= my_last_i; ++i) {
    res[i] = 0;
    for (int j = 0; j < n_cols; ++j) {
        res[i] += A[i * n_cols + j] * vec[j];
    }
}

Действия res[i] = 0 и накопление суммы — это записи в массив результата. При построчном размещении соседние значения res[i] физически могут попасть в одну кэш-линию, даже если логически назначены разным потокам.

Как измеряли

В конспекте N_ITER = 100. Перед серией запусков выделяют память под матрицу, вектор и результат, заполняют входы функцией rand() % 5, измеряют суммарное время цикла создания и присоединения потоков функцией GET_TIME из timer.h, а затем делят время на 100. Поэтому измерение включает накладные расходы pthread_create и pthread_join, повторяющиеся на каждой итерации.

Высокая матрица

8 млн × 8

Много строк, каждая короткая. При росте числа потоков из таблицы видно ускорение примерно в 2 раза для 2 потоков и 3.9 раза для 4 потоков.

Квадратная

8 тыс × 8 тыс

Большая матрица и длинные строки. Результаты тоже близки к линейному ускорению на 2 и 4 потоках в указанном замере.

Толстая и короткая

8 × 8 млн

Всего 8 результатов и очень длинный входной вектор. 2 потока почти не ускоряют, а 4 потока в замере даже медленнее одного.

Почему форма 8 × 8 млн плоха для масштабирования?

  1. Выходной массив содержит всего 8 элементов и очень мал.
  2. Разные потоки записывают разные элементы этого короткого массива: логически индексы не пересекаются, но значения могут находиться в одной кэш-линии.
  3. При каждой записи ядро получает владение линией, а копии на других ядрах могут инвалидироваться. Это и есть false sharing.
  4. Работы по количеству строк тоже мало: при 4 потоках на поток приходится около 2 строк. Накладные расходы управления могут стать заметными на фоне полезной работы.
Точность в типах данных

В текстовом объяснении конспекта говорится о восьми double в 64-байтовой линии, а исходный листинг объявляет int *A, int *vec и int *res. Для типичного int размером 4 байта одна 64-байтовая линия вмещает 16 элементов, а не 8. Главный вывод не меняется: 8 соседних int занимают лишь 32 байта и вполне могут совместно находиться в одной линии. Реальный размер линии нужно проверять для конкретной платформы.

Улучшенное разбиение строк на C

Все строки распределяются корректно
static void *routine(void *arg) {
    long rank = *(const long *)arg;
    long first = rank * n_rows / thread_count;
    long end = (rank + 1) * n_rows / thread_count; /* exclusive */

    for (long i = first; i < end; ++i) {
        long sum = 0;
        for (long j = 0; j < n_cols; ++j)
            sum += (long)A[i * n_cols + j] * vec[j];
        res[i] = (int)sum;
    }
    return NULL;
}

Предполагается, что n_rows и thread_count доступны потоку и согласованы по типам. Переданный rank должен указывать на индивидуальный объект, живущий до возврата потока. В реальном коде надо также проверить переполнение при вычислении индексов и размера выделений памяти.

Задача 1Базовая

Печать из N потоков

Условие. Прочитай N из аргумента командной строки, создай N потоков. Каждый должен вывести свой номер и общее число потоков. Main печатает собственную строку и дожидается всех рабочих потоков.

Требования. Выдели массив pthread_t, проверь аргументы, проверь ошибки создания, выполни pthread_join и освободи массив.

Подсказка
Стартовая функция должна иметь тип void *routine(void *arg). Аргумент передай через отдельный элемент массива long ranks[N] или структуры. Не передавай всем потокам &i.
Критерии готовности
Задача 2Передача аргументов

Структура с задачей

Условие. Создай struct Task { long rank; const char *title; long n; }. Каждый поток печатает поля и вычисляет сумму чисел от 1 до n. Main назначает потокам разные n и получает сумму от каждого.

Подсказка
Вводную структуру можно хранить в массиве в main. Для результата возвращай выделенный через malloc объект с суммой и освобождай его в main после pthread_join. Прежде чем кастовать void **, убедись, что знаешь тип указателя, который возвращается.

arg = (struct Task *)raw_arg
result = malloc(sizeof *result)
result->sum = 1 + 2 + ... + arg->n
return result

Добавь проверку ошибок, а также защиту от слишком большого n и переполнения суммы.

Задача 3Жизненный цикл

Сравни join и detach

Условие. Напиши две версии программы. Первая создаёт N потоков и делает join каждому. Вторая отсоединяет каждый поток. Пусть каждый поток печатает старт и завершение, используя небольшую работу (например, цикл или короткую вычислительную задачу).

Вопросы. Почему в detached-версии main может завершиться до строки «завершение»? Что изменится, если добавить отдельный механизм ожидания или задержку? Почему sleep не является корректной заменой синхронизации?

Что проверить
Вызов pthread_detach после каждого успешного создания; не вызывать join для detached-потока; помнить, что завершение процесса завершает оставшиеся потоки. Для достоверной координации лучше использовать join в joinable-сценарии или синхронизацию, подходящую для detached-сценария.
Задача 4Отмена

Кооперативная остановка

Условие. Рабочий поток обрабатывает большой цикл. Реализуй флаг остановки и завершение по просьбе main. Затем изучи, где применяются pthread_cancel, pthread_setcancelstate и pthread_setcanceltype.

Ограничение. Флаг, читаемый и записываемый из разных потоков, должен быть корректно синхронизирован — например, через C11 atomic_bool или mutex. Обычная переменная без синхронизации приведёт к data race.

Подсказка
Попробуй #include <stdatomic.h>, atomic_bool stop = false;, в цикле проверять atomic_load(&stop), а в main сделать atomic_store(&stop, true), затем join.
Задача 5Матричное умножение

A × vec

Условие. Реализуй умножение плотной матрицы на вектор с плоским построчным хранением. Распредели строки между N потоками. Проверь размеры 8000×8, 8000×8000 и 8×8000000, если доступной памяти достаточно.

Требования. Все строки результата должны вычисляться ровно один раз. Перед первым замером выдели и инициализируй входы. Измерь несколько повторов; отдельно оцени время вычисления и накладные расходы создания/присоединения потоков.

Подсказка: границы чанка
first = rank * n_rows / thread_count
end   = (rank + 1) * n_rows / thread_count
for (i = first; i < end; ++i) ...

Правая граница end не включается. Такая формула равномерно распределяет строки и не теряет остаток.

Проверка результата
Сначала напиши последовательную версию и сравни каждый элемент с многопоточной. Добавь тесты с N=1, N больше числа строк, нечётным количеством строк и квадратными матрицами маленького размера. Для времени укажи единицы и не делай выводов по одному запуску.
Задача 6Производительность

Найди и устрани false sharing

Условие. Запусти эксперимент, в котором каждый поток многократно увеличивает собственный счётчик в массиве соседних элементов. Измерь времена для 1, 2 и 4 потоков. Затем измени расположение данных, чтобы часто изменяемые счётчики разных потоков не делили кэш-линию.

Подсказка
Не делай каждый инкремент в общем атомике: это будет уже true sharing/контеншн. Лучше хранить отдельный счётчик на поток и менять расстояние/выравнивание между счётчиками. Учитывай, что 64 байта — типичное значение, а не универсальное правило. Повтори много раз и сравни медиану или устойчивые значения.

  2. routine имеет тип void *(void *).
  3. pthread_join(t, &result) ждёт один поток; pthread_detach(t) отключает возможность join.
  4. pthread_exit(ptr) завершает текущий поток с результатом ptr.
  5. False sharing: разные данные в одной кэш-линии → лишние инвалидирования и передачи владения.
  6. Параллельность надо измерять: накладные расходы и расположение данных могут перевесить выигрыш от дополнительных потоков.
