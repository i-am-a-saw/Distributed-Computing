Карта темы: какую проблему решает синхронизация?

Потоки внутри процесса могут обращаться к общей памяти. Чтобы взаимодействие было корректным, нужно согласовать доступ к данным и событиям.

Мьютекс — «ключ от комнаты»

Защищает критическую секцию: в один момент времени мьютексом владеет не более одного потока. Другие потоки ждут, пока владелец его освободит.

lock→критическая секция→unlock

Семафор — «счётчик разрешений»

Хранит неотрицательное количество разрешений. sem_wait забирает одно разрешение или блокируется; sem_post добавляет разрешение или будит ожидающий поток.

wait: −1↔счётчик↔post: +1
Главная разница: мьютекс отвечает на вопрос «кто сейчас владеет доступом?», а семафор — «сколько разрешений доступно?». Это не взаимозаменяемые понятия, даже если бинарный семафор иногда применяют для похожей задачи.

В конспекте рассматриваются два инструмента: pthread_mutex_t и sem_t. Они не создают потоки сами по себе — они синхронизируют уже созданные потоки или, при подходящем размещении семафора в общей памяти, процессы.

1

Мьютекс: инициализация, захват и освобождение

Мьютекс — примитив взаимного исключения (mutual exclusion), которому в pthreads соответствует тип pthread_mutex_t.

Интуитивно: когда поток успешно вызывает pthread_mutex_lock(&m), он захватывает мьютекс m и становится владельцем. Пока он владеет им, другой поток не может одновременно захватить тот же мьютекс обычным вызовом lock.

Три ключевые операции

ФункцияНазначениеНа что обратить внимание
pthread_mutex_init(&m, attr)Инициализировать объект мьютекса.attr задаёт атрибуты; NULL означает атрибуты по умолчанию.
pthread_mutex_lock(&m)Захватить мьютекс.Если им владеет другой поток, вызывающий обычно блокируется, пока мьютекс не освободят.
pthread_mutex_unlock(&m)Освободить мьютекс.Разблокировать его должен владелец. Попытка со стороны другого потока может быть ошибкой или неопределённым поведением — это зависит от типа.
pthread_mutex_destroy(&m)Освободить ресурсы объекта.Уничтожать можно после того, как работа с мьютексом завершена: его больше не держат и на нём не ждут.

Жизненный цикл

инициализация→lock→критическая секция→unlock→повторное использование→destroy

Пример защищённого инкремента:

Минимальная схема критической секции
pthread_mutex_lock(&mutex);
shared_counter++;      /* критическая секция */
pthread_mutex_unlock(&mutex);

Вызовы lock и unlock образуют пару. Между ними должны находиться только те операции, которые действительно требуют защиты. Если сделать критическую секцию слишком большой, потоки будут дольше ждать; если защитить не все обращения к общим данным, гонка всё равно возможна.

1. СвободенВладелец отсутствует
2. Захвачен потоком AA вошёл в защищённую область
3. Поток B ждётB продолжит после unlock от A
Правило владения: мьютекс не является обычной переменной-счётчиком. По смыслу его освобождает поток-владелец. Не используйте unlock как способ «разбудить» поток, если этот поток не захватывал мьютекс.

Создание атрибутов

В конспекте используется pthread_mutexattr_settype, чтобы выбрать тип мьютекса. Перед настройкой объект атрибутов необходимо инициализировать функцией pthread_mutexattr_init. Когда атрибут больше не нужен, его можно освободить через pthread_mutexattr_destroy.

Правильная последовательность инициализации атрибутов
pthread_mutex_t mutex;
pthread_mutexattr_t attr;

int rc = pthread_mutexattr_init(&attr);
if (rc != 0) { /* обработать rc */ }

rc = pthread_mutexattr_settype(&attr, PTHREAD_MUTEX_ERRORCHECK);
if (rc != 0) { /* обработать rc */ }

rc = pthread_mutex_init(&mutex, &attr);
if (rc != 0) { /* обработать rc */ }

pthread_mutexattr_destroy(&attr); /* сам mutex остаётся инициализирован */
/* ... работа с mutex ... */
pthread_mutex_destroy(&mutex);
Обработка ошибок pthreads: многие функции pthreads возвращают код ошибки напрямую, а не через errno. В таком случае диагностируют rc, например через strerror(rc); автоматический вызов perror после записи кода в переменную не является корректной общей схемой.

Три типа мьютексов

Тип задаётся вторым аргументом pthread_mutexattr_settype(&attr, type) до создания мьютекса.

ТипПовторный lock тем же потокомПопытка unlock чужого мьютексаКогда полезен
PTHREAD_MUTEX_NORMALПо конспекту — приводит к неопределённому поведению; стандартное описание обычно трактует повторный захват как самоблокировку (deadlock).Неопределённое поведение.Минимальная проверка ошибок; использовать только при корректном соблюдении протокола.
PTHREAD_MUTEX_ERRORCHECKВозвращается код ошибки, вместо безусловного самозацикливания.Возвращается ошибка, например EPERM для операции, которую нельзя выполнять текущему потоку.Отладка и обнаружение неверного использования мьютекса.
PTHREAD_MUTEX_RECURSIVEПовторный захват тем же владельцем допустим; ведётся счётчик захватов.Чужой поток не может законно освободить мьютекс.Редкие случаи, когда один поток повторно входит в код, защищённый одним и тем же мьютексом.

Как работает рекурсивный мьютекс?

Если поток A дважды вызывает lock на рекурсивном мьютексе, ему нужно выполнить два соответствующих unlock, чтобы мьютекс стал доступен другим потокам. Один unlock уменьшает внутренний счётчик, но не обязательно освобождает мьютекс полностью.

NORMAL

Без проверки ошибок

Неправильный протокол синхронизации может превратиться в зависание или неопределённое поведение.

ERRORCHECK

Проверка ошибок

Помогает обнаруживать повторный захват или попытку освобождения не владельцем.

RECURSIVE

Повторный захват

Допускает вложенный lock тем же потоком, но каждый захват обязан иметь парный unlock.

Не путай «не было сообщения об ошибке» с «код корректен». В листинге конспекта смена ERRORCHECK на NORMAL убирает сообщение, но не делает попытку освободить чужой мьютекс допустимой.

Дэдлок (deadlock): почему потоки могут навсегда остановиться

В таблице 1 конспекта два потока захватывают два мьютекса в противоположном порядке.

ВремяПоток 1Поток 2
0lock(m1) — получает m1lock(m2) — получает m2
1lock(m2) — ждёт поток 2lock(m1) — ждёт поток 1

Что держит поток 1?

Мьютекс m1. Для продолжения ему нужен m2, который удерживает поток 2.

Что держит поток 2?

Мьютекс m2. Для продолжения ему нужен m1, который удерживает поток 1.

Замкнутое ожидание: поток 1 не отпустит m1, пока не получит m2; поток 2 не отпустит m2, пока не получит m1. Ни один поток не может продвинуться к unlock.

Интерактивная модель

Нажми кнопку, чтобы показать взаимную блокировку и затем применить правило единого порядка захвата.

m1свободен
m2свободен
Потокивыполняются
Симуляция ждёт запуска.

Как избегать дэдлока

  1. Задать общий порядок захвата. Например, все потоки сначала берут m1, затем m2 — независимо от своей задачи.
  2. Сокращать время удержания. Не ждать ввода пользователя, сетевого ответа или другого длительного события, держа мьютекс без необходимости.
  3. Проектировать протокол освобождения. На каждом пути после успешного захвата должен существовать корректный путь к освобождению.
Согласованный порядок
/* Все потоки берут блокировки в одном и том же порядке. */
pthread_mutex_lock(&m1);
pthread_mutex_lock(&m2);

/* работа, которой нужны обе блокировки */

pthread_mutex_unlock(&m2);
pthread_mutex_unlock(&m1);

Единый порядок устраняет именно цикл ожидания для этой пары блокировок; сложные программы всё равно требуют анализа других зависимостей и блокировок.

Разбор листинга 1: ERRORCHECK и ошибка unlock

Пример на страницах 3–4 конспекта проверяет, что произойдёт, если один поток попытается освободить мьютекс, захваченный другим.

main: init ERRORCHECK→main: lock(m)→рабочий поток: unlock(m)→код ошибки

В этом примере главный поток захватывает m, а затем запускает рабочие потоки. Их функция вызывает pthread_mutex_unlock(&m), хотя мьютекс принадлежит main. Для типа PTHREAD_MUTEX_ERRORCHECK такая операция обнаруживается как ошибка. В Linux типичный код — EPERM, который соответствует сообщению вроде Operation not permitted.

Точная оговорка к исходному листингу: в нём вызывается pthread_mutexattr_settype(&attr, ...) без предварительного pthread_mutexattr_init(&attr). Так делать нельзя: объект атрибутов сначала должен быть инициализирован. В учебном примере ниже эта последовательность исправлена.
Иллюстрация идеи с корректной инициализацией и диагностикой
#define _XOPEN_SOURCE 700
#include <pthread.h>
#include <stdio.h>
#include <string.h>

static pthread_mutex_t m;

static void *worker(void *unused) {
    (void)unused;
    int rc = pthread_mutex_unlock(&m); /* этот поток не владелец */
    if (rc != 0) {
        fprintf(stderr, "worker unlock: %s (код %d)\n", strerror(rc), rc);
    }
    return NULL;
}

int main(void) {
    pthread_mutexattr_t attr;
    pthread_t thread;
    int rc = pthread_mutexattr_init(&attr);
    if (rc != 0) return 1;

    rc = pthread_mutexattr_settype(&attr, PTHREAD_MUTEX_ERRORCHECK);
    if (rc != 0) return 1;
    rc = pthread_mutex_init(&m, &attr);
    pthread_mutexattr_destroy(&attr);
    if (rc != 0) return 1;

    pthread_mutex_lock(&m); /* main становится владельцем */
    rc = pthread_create(&thread, NULL, worker, NULL);
    if (rc == 0) pthread_join(thread, NULL);
    pthread_mutex_unlock(&m);
    pthread_mutex_destroy(&m);
    return rc != 0;
}

Почему в диагностике используется strerror(rc), а не perror? Функции pthreads, которые возвращают ошибки в виде ненулевого результата, обычно возвращают сам номер ошибки. Они не обязаны записывать этот номер в errno. perror печатает расшифровку текущего errno, а это может оказаться совсем другая ошибка.

Вывод: ERRORCHECK полезен для поиска нарушений протокола синхронизации. Он не заменяет правильного владения, обработки кодов возврата и парных операций.

Семафоры: счётчик разрешений

В POSIX unnamed semaphore представлен типом sem_t. В конспекте он описан как беззнаковая целочисленная переменная; практически важно понимать его как синхронизационный объект со счётчиком.

Инициализация и удаление

Интерфейс из конспекта
#include <semaphore.h>

int sem_init(sem_t *sem, int pshared, unsigned int value);
int sem_wait(sem_t *sem);
int sem_post(sem_t *sem);
int sem_destroy(sem_t *sem);
Аргумент / функцияЗначение
sem_init(&s, 0, initial)pshared = 0: семафор предназначен для потоков одного процесса. Это вариант в листинге 2 конспекта.
sem_init(&s, 1, initial)Ненулевой pshared: семафор разделяется между процессами и должен располагаться в памяти, доступной этим процессам (например, в общей памяти).
initialНачальное количество разрешений. В кольцевом примере каждый семафор начинается с 0.
sem_wait(&s)Если счётчик больше 0 — уменьшает его на 1 и продолжает. Если счётчик равен 0 — блокирует поток до доступного разрешения.
sem_post(&s)Добавляет разрешение; если есть ожидающий поток, один из ожидающих может быть разблокирован.
sem_destroy(&s)Завершает жизненный цикл неименованного семафора; вызывать после окончания его использования.
Почему sem_init(..., 0, 0) удобно для событий? Нулевой счётчик означает: «разрешения пока нет». Поток-получатель останавливается на sem_wait и продолжит, когда отправитель вызовет sem_post.

Поиграй со счётчиком

Это модель семафора. Она показывает счётчик разрешений и ожидающих потоков. Начни с нуля и нажми Wait — появится заблокированный поток. Затем нажми Post: разрешение передастся ожидающему, и поток продолжит работу.

Бинарный и считающий семафор

Если ограничить счётчик уровнями 0 и 1, получается бинарный семафор — он может использоваться для простых задач взаимного исключения. Если счётчик допускает значения выше единицы, семафор удобно применять для ограничения числа одновременно используемых ресурсов, например пяти соединений или трёх устройств.

Отличие от мьютекса: у семафора нет понятия владельца. Один поток может выполнить sem_post, чтобы разрешить работу другому. У мьютекса корректное освобождение связано с потоком-владельцем.

Кольцевая передача сообщений: «производитель — потребитель»

В листинге 2 конспекта каждый поток отправляет сообщение следующему потоку по кругу, а затем ждёт сообщение для себя.

Для потока с номером my_rank вычисляются:

Получатель — dest

dest = (my_rank + 1) % thread_count

Последний поток отправляет сообщение потоку 0 благодаря операции остатка от деления.

Предшественник — source

source = (my_rank + thread_count - 1) % thread_count

Это поток, от которого текущий поток должен получить своё сообщение.

Порядок действий одного потока

  1. Создать строку сообщения, например "Hello from 1 to 2".
  2. Сохранить указатель на строку в messages[dest].
  3. Выполнить sem_post(&sems[dest]): сообщить потоку-получателю, что данные готовы.
  4. Выполнить sem_wait(&sems[my_rank]): дождаться сообщения, адресованного текущему потоку.
  5. Напечатать полученное сообщение.
Почему сначала записывают сообщение, а потом делают post? Получатель должен проснуться только после того, как данные подготовлены. Пара семафорных операций синхронизирует передачу: поток не просто угадывает момент, когда сообщение уже существует, а ожидает явного разрешения.

Интерактивная симуляция кольца

Поток 0ожидает сообщения
Поток 1ожидает сообщения
Поток 2ожидает сообщения
Поток 3ожидает сообщения
Выбери число потоков и запусти симуляцию.

Что именно происходит в коде из конспекта?

Основная логика потока из листинга 2
int dest = (my_rank + 1) % thread_count;
int source = (my_rank + thread_count - 1) % thread_count;

char *mes = malloc(MSG_SIZE * sizeof(char));
sprintf(mes, "Hello from %ld to %d", my_rank, dest);
messages[dest] = mes;
sem_post(&sems[dest]);
sem_wait(&sems[my_rank]);
printf("Thread %ld -> %s\n", my_rank, messages[my_rank]);

Обрати внимание: переменная source выводится формулой, но в исходном листинге явно не используется. Полученное сообщение извлекается через messages[my_rank]; источник уже определён тем, какой поток записал в этот слот. При запуске все семафоры имеют значение 0 — поток ждёт, пока его семафор не получит post.

Практические детали C: в оригинальном учебном коде показан принцип. В реальной программе нужно проверять результаты malloc, pthread_create, sem_init, sem_post и sem_wait, а также освобождать память. Не уничтожай семафор, пока какой-либо поток ещё может его использовать.

Полный рабочий пример на C: кольцо сообщений

Вариант для компиляции, основанный на идее листинга 2: по одному сообщению каждому следующему потоку, затем печать принятого сообщения.

Чтобы исключить тонкость преобразования целого числа в указатель в аргументе потока, здесь каждому потоку передаётся адрес структуры с номером. Обмен сообщений и использование семафоров соответствуют алгоритму конспекта.

ring_messages.c
#include <errno.h>
#include <pthread.h>
#include <semaphore.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

#define MSG_SIZE 100

typedef struct { int rank; } thread_arg;

static int thread_count;
static sem_t *sems;
static char **messages;

static void *routine(void *arg) {
    int rank = ((thread_arg *)arg)->rank;
    int dest = (rank + 1) % thread_count;
    char *msg = malloc(MSG_SIZE);
    if (msg == NULL) {
        fprintf(stderr, "malloc failed in thread %d\n", rank);
        messages[dest] = NULL;
    } else {
        snprintf(msg, MSG_SIZE, "Hello from %d to %d", rank, dest);
        messages[dest] = msg;
    }

    /* Даже при нехватке памяти сигнализируем получателю, чтобы он не ждал вечно. */
    if (sem_post(&sems[dest]) == -1) {
        perror("sem_post");
        abort();
    }

    while (sem_wait(&sems[rank]) == -1) {
        if (errno == EINTR) continue;
        perror("sem_wait");
        abort();
    }

    if (messages[rank] != NULL)
        printf("Thread %d -> %s\n", rank, messages[rank]);
    else
        fprintf(stderr, "Thread %d received no message (sender allocation failure)\n", rank);
    return NULL;
}

int main(int argc, char **argv) {
    if (argc != 2) {
        fprintf(stderr, "Usage: %s THREAD_COUNT (>= 1)\n", argv[0]);
        return 1;
    }
    char *end = NULL;
    long n = strtol(argv[1], &end, 10);
    if (*argv[1] == '\0' || *end != '\0' || n < 1 || n > 1000) {
        fprintf(stderr, "THREAD_COUNT must be from 1 to 1000\n");
        return 1;
    }
    thread_count = (int)n;

    pthread_t *threads = calloc((size_t)thread_count, sizeof(*threads));
    thread_arg *args = calloc((size_t)thread_count, sizeof(*args));
    sems = calloc((size_t)thread_count, sizeof(*sems));
    messages = calloc((size_t)thread_count, sizeof(*messages));
    if (!threads || !args || !sems || !messages) {
        perror("calloc");
        free(threads); free(args); free(sems); free(messages);
        return 1;
    }

    int initialized = 0;
    for (; initialized < thread_count; ++initialized) {
        if (sem_init(&sems[initialized], 0, 0) == -1) {
            perror("sem_init");
            for (int j = 0; j < initialized; ++j) sem_destroy(&sems[j]);
            free(threads); free(args); free(sems); free(messages);
            return 1;
        }
    }

    int created = 0;
    for (int i = 0; i < thread_count; ++i) {
        args[i].rank = i;
        int rc = pthread_create(&threads[i], NULL, routine, &args[i]);
        if (rc != 0) {
            fprintf(stderr, "pthread_create: %s\n", strerror(rc));
            break;
        }
        ++created;
    }

    /* Если не все потоки созданы, подаём разрешения, чтобы уже созданные
       потоки не остались бесконечно ждать отсутствующего участника кольца. */
    if (created != thread_count) {
        for (int i = 0; i < thread_count; ++i) sem_post(&sems[i]);
    }
    for (int i = 0; i < created; ++i) {
        int rc = pthread_join(threads[i], NULL);
        if (rc != 0) fprintf(stderr, "pthread_join: %s\n", strerror(rc));
    }

    for (int i = 0; i < thread_count; ++i) {
        sem_destroy(&sems[i]);
        free(messages[i]);
    }
    free(messages); free(sems); free(args); free(threads);
    return created == thread_count ? 0 : 1;
}
Важная учебная оговорка к обработке частичного запуска: блок с дополнительными sem_post нужен, чтобы потоки, созданные до ошибки pthread_create, не ждали несуществующего участника. Для промышленного кода error-path стоит проектировать и тестировать отдельно, особенно учитывая владение выделенной памятью и успешность каждой синхронизационной операции.

Как скомпилировать и запустить в Linux / WSL

Терминал
gcc -std=c11 -Wall -Wextra -Wpedantic -pthread ring_messages.c -o ring_messages
./ring_messages 4

В выводе порядок строк может различаться: планировщик ОС выбирает, в каком порядке запустятся потоки. Смысл результата — каждый поток печатает сообщение, которое адресовано ему его предшественником. Не требуется, чтобы строки выводились в порядке рангов.

Выбирай примитив по смыслу задачи — не только по тому, может ли он блокировать поток.

А. Два потока увеличивают одну общую переменную. Нужно не потерять инкременты.

Практикум: задачи на написание C-кода

Сначала попробуй решить самостоятельно. Подсказка направляет ход мысли; решение открывай после попытки. Код можно копировать в редактор.

1

Защити общий счётчик

Напиши программу с двумя потоками. Каждый увеличивает глобальный long counter 100 000 раз. Итог должен быть 200 000.

Подсказка и решение

Защищать нужно и сам инкремент, потому что он не является одной неделимой операцией на уровне языка C.

Фрагмент рабочей функции
static pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
static long counter = 0;

void *worker(void *arg) {
    (void)arg;
    for (int i = 0; i < 100000; ++i) {
        pthread_mutex_lock(&m);
        ++counter;
        pthread_mutex_unlock(&m);
    }
    return NULL;
}

Допиши в main создание двух потоков, два pthread_join, печать результата и затем pthread_mutex_destroy. Для учебного задания также обработай ошибки API.

2

Найди ошибку протокола с мьютексом

Главный поток захватил m. Рабочий поток вызывает pthread_mutex_unlock(&m). Объясни разницу поведения для NORMAL и ERRORCHECK.

Подсказка и решение

Нельзя освобождать обычный мьютекс из потока, который им не владеет. ERRORCHECK возвращает код ошибки; NORMAL не превращает ошибочную операцию в корректную — поведение неопределено. Инициализация атрибутов должна идти через pthread_mutexattr_init до pthread_mutexattr_settype.

3

Устрани дэдлок в двух ресурсах

Поток A берёт m1, затем m2; поток B берёт m2, затем m1. Перепиши порядок и укажи порядок освобождения.

Подсказка и решение

Договоритесь, что все потоки захватывают блокировки в одном порядке: сначала m1, затем m2. Для естественного стека освобождения отпускайте наоборот: сначала m2, затем m1. Важно, чтобы все участки программы соблюдали общий порядок.

4

Передай событие с помощью семафора

Есть два потока. Получатель должен напечатать «данные готовы» только после того, как производитель записал данные. Инициализируй семафор правильно и расставь wait/post.

Подсказка и решение
Схема синхронизации
/* main: */
sem_t ready;
sem_init(&ready, 0, 0);  /* первоначально разрешения нет */

/* producer thread: */
prepare_data();
sem_post(&ready);       /* событие: данные готовы */

/* consumer thread: */
sem_wait(&ready);       /* ждёт разрешения */
use_data();

Перед использованием общие данные должны быть организованы так, чтобы производитель и потребитель обращались к одному объекту. Не уничтожай семафор, пока потоки ещё работают.

5

Измени кольцо на 5 потоков

В коде листинга оставь формулы dest и source. Проследи, кто отправляет сообщение потоку 0 и от кого оно приходит.

Подсказка и решение

Для ранга 4 при thread_count = 5: dest = (4 + 1) % 5 = 0. Для ранга 0: source = (0 + 5 - 1) % 5 = 4. Поэтому поток 4 отправляет сообщение потоку 0, а поток 0 получает сообщение от потока 4.

6

Ограничь доступ к трём ресурсам

Напиши псевдокод потока, который перед использованием одного из трёх ресурсов уменьшает счётчик семафора, а после освобождения увеличивает его. Что произойдёт с четвёртым потоком?

Подсказка и решение
Псевдокод
sem_wait(&slots);   /* slots инициализирован значением 3 */
use_limited_resource();
sem_post(&slots);   /* ресурс освобождён */

Первые три потока могут получить разрешения. Дополнительный поток заблокируется в sem_wait, если все три разрешения уже использованы, и продолжит после sem_post одним из потоков.
