Барьеры и условные переменные в pthreads

Научимся синхронизировать потоки так, чтобы никто не начинал следующий этап раньше остальных. Разберём три подхода из конспекта, их слабые места, корректный многоразовый барьер и передачу сообщений по кругу.

01

Что такое барьер

Ключевое определение с первой страницы конспекта.

ОпределениеБарьер — фрагмент кода, из которого ни один поток не выйдет, пока в него не зашёл последний участвующий поток.

Представьте команду из четырёх потоков, каждый из которых обрабатывает свою часть данных. Все выполняют этап A, но этап B можно начинать только тогда, когда каждый закончил A. Барьер — точка коллективного ожидания: быстрые потоки ждут медленный.

Схема барьера: потоки прибывают в разное время
Поток 0
Этап AожидаетЭтап B
Поток 1
Этап AожидаетЭтап B
Поток 2
Этап Aдошёл последним → отпускает барьер
Поток 3
Этап AожидаетЭтап B

Барьер не то же самое, что мьютекс

Мьютекс защищает критическую секцию так, чтобы владеть ею мог один поток. Барьер синхронизирует группу: всем нужно достичь определённой точки.

Барьер не обязательно передаёт данные

Его задача — согласовать момент продолжения. Для безопасного доступа к общим данным всё равно нужны корректные правила синхронизации и видимости памяти.

Интерактивная модель: кто уже прибыл?

Нажми «Привести следующий поток». Пока не прибудут все 4 потока, никто не перейдёт на следующий этап.

0 из 4
Все потоки выполняют работу. Начни отмечать прибывшие потоки.
Проверка пониманияЕсли три потока из четырёх уже пришли, но четвёртый всё ещё вычисляет, три первых не должны пройти барьер. Иначе этап B может увидеть незавершённые результаты этапа A.
02

Подход 1. Холостой цикл (busy waiting)

Самый простой вариант из листинга 1, но не лучший для настоящей программы.

В конспекте используются четыре потока и десять тысяч барьеров: NTHREADS = 4, NBARRIERS = 10000. Каждый поток под мьютексом увеличивает counter[j], затем крутится в цикле, пока счётчик не станет равен числу потоков.

Идея листинга 1 · сокращённый фрагмент
for (int j = 0; j < NBARRIERS; ++j) {
    pthread_mutex_lock(&mutex);
    counter[j]++;
    pthread_mutex_unlock(&mutex);

    /* Холостое ожидание */
    while (counter[j] != NTHREADS) {
        /* пусто: поток постоянно проверяет условие */
    }
}

Что делает каждая строка

1. Учёт прибывших

lock → counter[j]++ → unlock не даёт двум потокам одновременно потерять инкремент общего счётчика. Без мьютекса операции «прочитать, прибавить, записать» могли бы конфликтовать.

2. Активное ожидание

Цикл непрерывно читает значение счётчика. Он не переводит поток в состояние ожидания через ОС, а продолжает занимать процессорное время, пока условие ложно.

Серьёзная проблема исходного фрагментаЧтение counter[j] в цикле происходит без мьютекса, одновременно с записями других потоков. Для обычного C int это гонка данных (data race) и неопределённое поведение. При -O2 компилятор может вынести чтение из цикла, и поток будет ждать бесконечно. Одной лишь вставки volatile для корректной межпоточной синхронизации недостаточно.

Три недостатка, которые подчёркивает конспект

Производительность

Потоки заняты ожиданием

Если запущенных потоков больше, чем доступных процессорных ядер, ожидающие потоки вытесняют полезную работу и ухудшают производительность.

Оптимизация

Оптимизатор не видит протокол

Компилятор может оптимизировать цикл, поскольку обычное чтение общей переменной не говорит ему, что другой поток её меняет. В корректном C это прежде всего data race.

Много барьеров

Счётчик одноразовый

Счётчик для данного этапа не обнуляется согласованно после прохода всеми потоками. В конспекте поэтому заводится массив counter[NBARRIERS], по одному счётчику на барьер.

Измерение в листинге 1 сделано через макрос GET_TIME из подключаемого timer.h: фиксируется начало, создаются 4 потока, главный поток вызывает pthread_join для каждого и печатает общее время. При NBARRIERS = 10000 измеряется прохождение серии барьеров, а не время одного барьера. Определение timer.h в конспекте не приведено.

Проверка: почему нельзя просто добавить volatile?

Ответ: volatile ограничивает некоторые оптимизации обращений к объекту, но не делает инкремент атомарным и не устанавливает полноценную синхронизацию между потоками. Используй mutex, атомики C11 с правильной моделью памяти или библиотечный примитив ожидания.

03

Подход 2. Семафоры

Ожидание без постоянного опроса счётчика.

В листинге 2 используется sem_t. У семафора есть целочисленное значение, не уходящее ниже нуля. sem_wait уменьшает положительное значение на 1; если оно равно 0, поток блокируется. sem_post добавляет 1 и может разблокировать ожидающий поток.

sem_count — защита счётчика

Инициализируется значением 1. Это семафор, похожий по применению на бинарный мьютекс: он не даёт двум потокам одновременно менять counter.

sem_barrier[j] — ворота данного этапа

Каждый барьерный семафор стартует с 0. Не последние потоки ждут на нём, а последний прибывший публикует столько разрешений, сколько нужно ожидающим потокам.

Интерактивный счётчик семафора

0
Ожидающих: 0
Значение 0: вызов sem_wait() заблокирует поток, пока не появится разрешение.

Алгоритм из конспекта, шаг за шагом

  1. Поток вызывает sem_wait(&sem_count), чтобы войти в защищённую область.
  2. Если до него пришли уже NTHREADS - 1 потоков, текущий — последний: он обнуляет counter, отпускает sem_count и выполняет NTHREADS - 1 вызовов sem_post(&sem_barrier[j]).
  3. Иначе поток увеличивает counter, отпускает sem_count и блокируется на sem_barrier[j].
  4. Когда последний поток публикует разрешения, ожидающие потоки могут продолжить выполнение этапа.
Логика барьера на семафорах из листинга 2
sem_wait(&sem_count);
if (counter == NTHREADS - 1) {
    counter = 0;
    sem_post(&sem_count);
    for (int i = 0; i < NTHREADS - 1; ++i)
        sem_post(&sem_barrier[j]);
} else {
    counter++;
    sem_post(&sem_count);
    sem_wait(&sem_barrier[j]);
}
Нюанс к объяснению в PDFКонспект утверждает, что семафор барьера может остаться ненулевым, если разбуженные потоки временно не запланированы ОС, и поэтому его нельзя переиспользовать. В стандартной семантике семафора разрешения sem_post сохраняются: позднее вызванный sem_wait потребит сохранённое разрешение. В показанном коде к тому же выделяется отдельный sem_barrier[j] для каждого j-го барьера — он не переиспользуется между раундами. Практический вывод остаётся важным: при проектировании многоразового барьера нельзя позволять разрешениям одной фазы ошибочно выпускать потоки через другую фазу; нужно чётко разделять поколения.

В листинге создаётся массив семафоров размером NBARRIERS, каждый инициализируется sem_init(&sem_barrier[i], 0, 0); shared = 0 означает разделение между потоками одного процесса. sem_count начинается с 1. После pthread_join семафоры очищаются через sem_destroy. В этом листинге также объявлен и инициализирован pthread_mutex_t mutex, но для защиты счётчика фактически используется sem_count; объявленный мьютекс алгоритму не нужен. Время серии из 10000 барьеров измеряется тем же GET_TIME.

04

Подход 3. Условные переменные

pthread_cond_t сообщает потокам, что состояние, которого они ждут, могло измениться.

Условная переменная применяется вместе с мьютексом. Сама по себе она не хранит «истинность условия» и не заменяет переменную-предикат. Состояние задаётся отдельными данными — например, количеством прибывших потоков или флагом готовности.

Инициализация и уничтожение

pthread_cond_init(&cond, NULL) создаёт условную переменную с атрибутами по умолчанию.

pthread_cond_destroy(&cond) освобождает её ресурсы после того, как никто больше её не использует и не ждёт на ней.

Сигнализация

pthread_cond_signal(&cond) пробуждает один поток из ждущих (какой именно — не гарантируется).

pthread_cond_broadcast(&cond) пробуждает все потоки, которые ждут на этой условной переменной.

Шпаргалка API

Основные прототипы pthread condition variables
int pthread_cond_init(pthread_cond_t *cond,
                      const pthread_condattr_t *attr);
int pthread_cond_destroy(pthread_cond_t *cond);
int pthread_cond_wait(pthread_cond_t *cond, pthread_mutex_t *mutex);
int pthread_cond_signal(pthread_cond_t *cond);
int pthread_cond_broadcast(pthread_cond_t *cond);

Самое важное: что делает pthread_cond_wait

Три действия одной операции ожидания
Шаг 1

Отпускает мьютекс

Атомарно относительно ожидания: другой поток может зайти и изменить общее условие.

Шаг 2

Ждёт сигнал

Ожидающий поток не крутится в пустом цикле и не занимает CPU постоянными проверками.

Шаг 3

Захватывает мьютекс снова

Функция возвращается только после повторного захвата переданного мьютекса.

Концептуальная схема pthread_cond_wait
pthread_mutex_unlock(&mutex);
wait_on_signal(&cond);
pthread_mutex_lock(&mutex);

Это псевдокод внутреннего поведения из конспекта, а не инструкция вызывать три функции вручную. Пользовательский код вызывает только pthread_cond_wait(&cond, &mutex); отпускание и повторный захват мьютекса функция организует сама.

Почему ожидание проверяется через while, а не через ifВозможен spurious wakeup — поток возвращается из ожидания даже без полезного сигнала для нужного условия. Кроме того, сигнал не гарантирует, что условие всё ещё истинно к моменту, когда поток вновь получит мьютекс. Поэтому поток обязан повторно проверять предикат под мьютексом: while (!condition) pthread_cond_wait(...);.

Корректный шаблон ожидания

Проверяем состояние под тем же мьютексом
pthread_mutex_lock(&mutex);
while (!condition) {
    pthread_cond_wait(&cond, &mutex);
}
/* Условие проверено при захваченном mutex */
use_shared_state();
pthread_mutex_unlock(&mutex);

Поток, который меняет условие, тоже должен работать с соответствующим общим состоянием под этим мьютексом. Типовой порядок: заблокировать мьютекс → изменить предикат → вызвать signal или broadcast → разблокировать мьютекс.

05

Барьер на условной переменной

Листинг 3 из конспекта и важные условия его корректности.

Переменные листинга: mutex защищает счётчик counter; cond используется для пробуждения; NTHREADS задаёт число участников. Каждый поток входит в критическую секцию и увеличивает счётчик. Последний сбрасывает его и будит остальных.

Логика из конспекта, с сохранением существенной строки ожидания
pthread_mutex_lock(&mutex);
counter++;
if (counter == NTHREADS) {
    counter = 0;
    pthread_cond_broadcast(&cond);
} else {
    while (pthread_cond_wait(&cond, &mutex) != 0) ;
}
pthread_mutex_unlock(&mutex);
Важное замечание к исходному листингуЦикл while (pthread_cond_wait(...) != 0) повторяет ожидание только при ненулевом коде возврата. Он не проверяет предикат и потому не защищает от spurious wakeup. Более того, просто исправить условие на while (counter < NTHREADS) недостаточно для многоразового барьера: последний поток сбрасывает счётчик в 0, а быстрый поток может начать следующий раунд до того, как все потоки предыдущего раунда окончательно вышли. Нужен номер поколения (generation).

Исправленная версия: многоразовый барьер

Здесь у барьера хранится count — сколько потоков прибыло в текущем раунде, и generation — номер раунда. Каждый поток запоминает поколение при входе и ждёт, пока поколение изменится. Последний поток сбрасывает счётчик, увеличивает номер поколения и делает broadcast.

Компилируемый пример reusable barrier
#include <pthread.h>
#include <stdio.h>
#include <stdlib.h>

#define NTHREADS 4
#define ROUNDS 5

typedef struct {
    pthread_mutex_t mutex;
    pthread_cond_t cond;
    unsigned count;
    unsigned generation;
    unsigned parties;
} barrier_t;

int barrier_init(barrier_t *b, unsigned parties) {
    if (parties == 0) return -1;
    b->count = 0;
    b->generation = 0;
    b->parties = parties;
    if (pthread_mutex_init(&b->mutex, NULL) != 0) return -1;
    if (pthread_cond_init(&b->cond, NULL) != 0) {
        pthread_mutex_destroy(&b->mutex);
        return -1;
    }
    return 0;
}

void barrier_wait(barrier_t *b) {
    pthread_mutex_lock(&b->mutex);
    unsigned my_generation = b->generation;
    b->count++;

    if (b->count == b->parties) {
        b->count = 0;
        b->generation++;
        pthread_cond_broadcast(&b->cond);
    } else {
        while (my_generation == b->generation) {
            pthread_cond_wait(&b->cond, &b->mutex);
        }
    }
    pthread_mutex_unlock(&b->mutex);
}

void barrier_destroy(barrier_t *b) {
    pthread_cond_destroy(&b->cond);
    pthread_mutex_destroy(&b->mutex);
}

barrier_t barrier;
void *worker(void *arg) {
    long rank = (long)arg;
    for (int r = 0; r < ROUNDS; ++r) {
        printf("thread %ld: work in round %d\n", rank, r);
        barrier_wait(&barrier);
        printf("thread %ld: passed round %d\n", rank, r);
    }
    return NULL;
}

int main(void) {
    pthread_t threads[NTHREADS];
    if (barrier_init(&barrier, NTHREADS) != 0) {
        fputs("barrier_init failed\n", stderr);
        return EXIT_FAILURE;
    }
    for (long i = 0; i < NTHREADS; ++i)
        if (pthread_create(&threads[i], NULL, worker, (void *)i) != 0) {
            perror("pthread_create");
            return EXIT_FAILURE;
        }
    for (int i = 0; i < NTHREADS; ++i)
        pthread_join(threads[i], NULL);
    barrier_destroy(&barrier);
    return 0;
}
Почему поколение решает проблемуПоток ждёт не просто «пока счётчик станет нулём или достигнет порога», а пока изменится конкретный раунд, в котором он прибыл. Сигнал прошлого раунда не удовлетворит условие для следующего раунда. Проверка идёт в цикле под мьютексом, поэтому spurious wakeup безопасен.

Как и в листинках 1–2, исходный листинг 3 замеряет серию из NBARRIERS = 10000 синхронизаций и печатает разность end - start; вызовы GET_TIME определены во внешнем для конспекта заголовке timer.h.

Сборка на Linux/WSL: gcc -std=c11 -Wall -Wextra -O2 barrier.c -o barrier -pthread, затем ./barrier. Для краткости обработка ошибок во время создания нескольких потоков в учебном примере не выполняет полный откат уже созданных потоков; в промышленном коде такой cleanup необходимо добавить.

06

Передача сообщений по кругу

Второй пример с условными переменными из конспекта: каждый поток отправляет сообщение следующему.

Для потока с номером my_rank получатель вычисляется формулой dest = (my_rank + 1) % thread_count. Остаток от деления замыкает цепочку: поток с последним номером отправляет сообщение потоку 0. Массив messages[dest] хранит указатель на сообщение для получателя, а cond[dest] — условную переменную, на которой получатель может ждать.

5
Каждый поток отправит «Hello to DEST from SRC» следующему потоку.

Разбор исходного алгоритма

  1. Поток вычисляет dest и выделяет буфер сообщения.
  2. Формирует текст наподобие Hello to 3 from 2 и помещает указатель в messages[dest].
  3. Блокирует общий мьютекс, сигнализирует cond[dest], а затем проверяет, пришло ли сообщение в собственный слот messages[my_rank].
  4. Если собственного сообщения ещё нет, поток вызывает pthread_cond_wait, затем разблокирует мьютекс и печатает принятое сообщение.
  5. Главный поток присоединяет все потоки через pthread_join, после чего освобождает строки, уничтожает условные переменные и мьютекс.
Существенный фрагмент листинга 4
long dest = (my_rank + 1) % thread_count;
char *my_msg = malloc(MSG_MAX * sizeof(char));
sprintf(my_msg, "Hello to %ld from %ld", dest, my_rank);
messages[dest] = my_msg;

pthread_mutex_lock(&mutex);
pthread_cond_signal(&cond[dest]);
if (messages[my_rank] == NULL)
    pthread_cond_wait(&cond[my_rank], &mutex);
pthread_mutex_unlock(&mutex);

printf("Thread %ld > %s\n", my_rank, messages[my_rank]);
Что стоит усилить по сравнению с исходным листингомУсловие перед ожиданием нужно проверять циклом while, а чтение и запись слотов messages[] — выполнять под одним мьютексом. В исходном фрагменте запись messages[dest] = my_msg выполняется вне мьютекса, поэтому возможна гонка с чтением слота получателем. Кроме того, строка-предикат должна быть защищена тем же мьютексом, что и переход в ожидание: это закрывает окно между проверкой условия и ожиданием.

Безопаснее организованный шаблон обмена

Полная компилируемая версия ring.c
#include <pthread.h>
#include <stdio.h>
#include <stdlib.h>
#include <errno.h>

#define MAX_THREADS 1024
#define MSG_MAX 100

int thread_count;
char **messages;
pthread_cond_t *cond;
pthread_mutex_t mutex;

static void *Send_msg(void *arg) {
    long my_rank = *(long *)arg;
    long dest = (my_rank + 1) % thread_count;
    char *my_msg = malloc(MSG_MAX);
    if (my_msg == NULL) return NULL;
    snprintf(my_msg, MSG_MAX, "Hello to %ld from %ld", dest, my_rank);

    pthread_mutex_lock(&mutex);
    messages[dest] = my_msg;
    pthread_cond_signal(&cond[dest]);
    while (messages[my_rank] == NULL) {
        pthread_cond_wait(&cond[my_rank], &mutex);
    }
    char *received = messages[my_rank];
    pthread_mutex_unlock(&mutex);

    printf("Thread %ld > %s\n", my_rank, received);
    return NULL;
}

int main(int argc, char **argv) {
    if (argc != 2) {
        fprintf(stderr, "Usage: %s THREAD_COUNT\n", argv[0]);
        return EXIT_FAILURE;
    }
    char *end = NULL;
    errno = 0;
    long n = strtol(argv[1], &end, 10);
    if (errno != 0 || end == argv[1] || *end != '\0' || n < 2 || n > MAX_THREADS) {
        fprintf(stderr, "THREAD_COUNT must be in [2, %d]\n", MAX_THREADS);
        return EXIT_FAILURE;
    }
    thread_count = (int)n;
    pthread_t *threads = calloc((size_t)thread_count, sizeof(*threads));
    long *ranks = calloc((size_t)thread_count, sizeof(*ranks));
    messages = calloc((size_t)thread_count, sizeof(*messages));
    cond = calloc((size_t)thread_count, sizeof(*cond));
    if (!threads || !ranks || !messages || !cond) {
        perror("calloc");
        return EXIT_FAILURE;
    }
    if (pthread_mutex_init(&mutex, NULL) != 0) {
        fprintf(stderr, "pthread_mutex_init failed\n");
        return EXIT_FAILURE;
    }
    for (long i = 0; i < thread_count; ++i) {
        ranks[i] = i;
        if (pthread_cond_init(&cond[i], NULL) != 0) {
            fprintf(stderr, "pthread_cond_init failed\n");
            return EXIT_FAILURE;
        }
    }
    for (long i = 0; i < thread_count; ++i) {
        int rc = pthread_create(&threads[i], NULL, Send_msg, &ranks[i]);
        if (rc != 0) {
            fprintf(stderr, "pthread_create failed: %d\n", rc);
            return EXIT_FAILURE;
        }
    }
    for (int i = 0; i < thread_count; ++i) pthread_join(threads[i], NULL);

    for (int i = 0; i < thread_count; ++i) {
        free(messages[i]);
        pthread_cond_destroy(&cond[i]);
    }
    pthread_mutex_destroy(&mutex);
    free(cond);
    free(messages);
    free(ranks);
    free(threads);
    return EXIT_SUCCESS;
}

Это шаблон только для одного раунда с единственной записью в каждый слот. Для повторяющихся раундов нужно обнулить/потребить слот, договориться о владении памятью сообщений и добавить идентификатор поколения или очередь; иначе старые значения могут быть приняты за новые.

Задача 1 Проследить барьер для 4 потоков
Уровень: базовыйСимуляция выше

Запиши по шагам, что произойдёт, если потоки 1, 3 и 0 увеличили счётчик, а поток 2 ещё не дошёл. Кто может продолжить работу и почему?

Разбор: счётчик равен 3 из 4. Потоки, которые уже дошли, должны ждать. После прибытия потока 2 условие количества участников выполнено и можно выпускать все четыре. Холостой цикл из конспекта пытается это обнаружить постоянным чтением counter, но его чтение без синхронизации некорректно в модели памяти C.
Задача 2 Найти ошибки в busy waiting

В этом фрагменте есть две разные проблемы. Назови их и предложи корректное направление исправления.

Код для анализа
counter++;
while (counter != NTHREADS) { }
Ответ: (1) инкремент может терять обновления, если счётчик общий и не защищён; (2) чтение в пустом цикле активно расходует CPU и, если оно не синхронизировано, является гонкой данных. На практике — защищать изменение общего состояния и предпочтительно использовать корректный блокирующий примитив, например условную переменную с mutex и проверкой предиката в while.
Задача 3 Реализовать многоразовый барьер
Уровень: среднийpthread_mutex_t + pthread_cond_t

Реализуй функцию barrier_wait для структуры с полями count, parties и generation. Требование: барьер должен корректно проходиться минимум 100 раз каждым потоком.

pthread_mutex_lock(&b->mutex);
unsigned g = b->generation;
if (++b->count == b->parties) {
    b->count = 0;
    ++b->generation;
    pthread_cond_broadcast(&b->cond);
} else {
    while (g == b->generation)
        pthread_cond_wait(&b->cond, &b->mutex);
}
pthread_mutex_unlock(&b->mutex);

Почему работает: последний меняет поколение до пробуждения, а остальные ждут именно изменения поколения своего раунда.

Задача 4 Исправить ожидание условной переменной

Перепиши цикл из листинга 3 так, чтобы он учитывал и spurious wakeup, и многоразовое использование барьера. Объясни, почему простой if не подходит.

Ключ: запомнить generation под мьютексом; увеличить count; последний участник обнуляет count, инкрементирует generation и вызывает broadcast; остальные ожидают в while (old_generation == generation) pthread_cond_wait(...). Цикл должен проверять условие, а не код возврата функции ожидания.
Задача 5 Написать кольцевую рассылку
Уровень: среднийМассив сообщений

Создай N потоков. Каждый отправляет строку следующему участнику, ждёт собственное сообщение и печатает его. Используй dest = (rank + 1) % N, общий mutex и по одной условной переменной на получателя. Публикация указателя и проверка messages[rank] должны быть защищены одним и тем же mutex.

Задача 6 Измерить время

На основе листингов конспекта измерь время тысяч проходов для: (A) активного ожидания, (B) семафоров, (C) условных переменных. Проведи тест при числе потоков не больше числа CPU и при большем числе. Сформулируй, почему результаты меняются.

Фиксируй одну и ту же машину, компилятор, флаги сборки, число раундов, число потоков и входные данные. Запускай несколько раз и сравнивай медиану. Busy waiting часто страдает при oversubscription, но примитивы блокировки также имеют издержки переключения контекста: измерения нужны для конкретной нагрузки, а не для универсального тезиса «один всегда быстрее».

Финальная карта понятий

Если можешь объяснить каждую строку без подсказки — основа семинара усвоена.

Термины

  • Barrier: все участники достигают одной точки прежде, чем продолжить.
  • Busy waiting: ожидание через повторную проверку условия.
  • Semaphore: счётчик разрешений; wait потребляет разрешение, post добавляет.
  • Condition variable: механизм ожидания изменения состояния в связке с mutex.
  • Spurious wakeup: возврат из ожидания не означает, что предикат истинен.
  • Generation: номер раунда для корректного повторного использования барьера.
